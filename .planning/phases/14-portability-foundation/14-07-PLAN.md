<objective>
Close the one functional defect this phase itself introduced. 14-01 moved the agent mention aliases
into `AGENT_MENTION_ALIASES` (code default `agent`) and deleted the hardcoded `@grooveos`/`@groove`/
`@gr`/`@g` regex from `mention_detector.py`. But the 5 `promptPrefix` system prompts in
`infrastructure/librechat/librechat.yaml.template` still tell users to mention **`@groove`** — an
alias that no longer exists by default.

Consequences today:
- A **self-hoster** boots with the default alias `agent`. The shipped system prompt tells them to type
  `@groove`. Nothing resolves. This is exactly the PORT-01/PORT-02 promise ("point it at your own
  deployment via config alone") failing in the most visible place — the assistant's own instructions.
- The xbrain deployment is about to move its alias list to `chad`-based (rebrand to teamchad.ai), at
  which point `@groove` stops resolving there too.

14-06's acceptance gate CANNOT catch this: check (a) greps the lowercase bare token `grooveos`, and
neither `GrooveOS` (title-case) nor `@groove` matches it. The phase would certify green with a false
instruction shipped.
</objective>

<design>
14-03b already built the exact mechanism needed: `apps/librechat/patches/render-config-entrypoint.sh`
renders `librechat.yaml.template` -> `librechat.yaml` at container start using a **filtered** envsubst
(currently `$LIBRECHAT_ALLOWED_DOMAINS $BRIDGE_BASE_URL $APP_TEAMS_URL`). The filter is deliberate:
every other `${VAR}` is left for LibreChat's own native per-field substitution. Extend it by exactly
one var — do not widen it further.

**Single source of truth.** Do NOT add a separate "display alias" env var — a second knob would
silently drift from the real alias list. Instead the entrypoint DERIVES it:

    AGENT_MENTION_PRIMARY = first comma-separated entry of AGENT_MENTION_ALIASES, default "agent"

Because `mention_detector` treats the alias list as a SET (order carries no meaning server-side),
ordering the list is a free, purely-cosmetic lever: a deployment that wants the prompt to say `@chad`
sets `AGENT_MENTION_ALIASES=chad,agent` — the prompt shows `@chad`, and BOTH `@chad` and `@agent`
still resolve. A deployment that changes nothing shows `@agent`. The displayed alias is therefore
always an alias that actually works, by construction.
</design>

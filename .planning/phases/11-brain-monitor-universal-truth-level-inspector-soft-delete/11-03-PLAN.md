# Plan 11-03 — Qdrant `deleted_at_ts` payload + filter

## Section 1 — Goal

Extend the Qdrant point payload written by `NativeProvider.upsert()` with a `deleted_at_ts` numeric field (Unix epoch seconds, `0.0` = not deleted), backfill every pre-Phase-11 Qdrant point so the new search filter does not blackhole legacy content, and add a `must_not` Range filter to `NativeProvider.search()` so soft-deleted memory_items disappear from semantic search results without requiring a Qdrant point delete. Also expose a helper to flip `deleted_at_ts` on existing points when memory-api processes a soft-delete (called by plan 11-05 PATCH/DELETE handlers).

Without this plan, soft-deleted memory_items continue to surface in `POST /v1/memory/search` because the vector retriever returns their IDs and the post-fetch PG query (patched in 11-06) cannot filter what the vector layer already prioritized. This plan plus 11-06 together close the regression.

## Section 1b — Deployment gate (REVISION 1 — fixes B-4)

The three tasks in this plan MUST ship in three atomic commits with a deployment-time ordering constraint:

1. **Task 1 (Qdrant backfill script + run)** — MUST execute against the live Qdrant instance AFTER Task 2 has shipped (so new upserts already write `deleted_at_ts=0.0` and don't race) and BEFORE Task 3 (the search filter) is merged to main. Order: **deploy Task 2 → run Task 1 backfill → merge Task 3**.
2. **Task 2 (upsert writes `deleted_at_ts=0.0`)** — safe to ship at any time; idempotent on already-tagged points.
3. **Task 3 (search filter `Range(lte=0.0)`)** — MUST NOT be merged to main until Task 1's backfill report (logged `before_count == after_count`) is captured.

**Rationale:** RESEARCH §Q3 Critical Pitfall — Qdrant `Range(lte=0.0)` does NOT match points where the payload field is absent. If Task 3 ships before backfill, every pre-Phase-11 memory point becomes invisible to search.

The executor MUST split these into separate commits and pause between commit 2 and commit 3 to confirm the backfill log line `[backfill] OK: before_count=N == after_count=N` on the production Qdrant instance.

## Section 3 — Tasks

### Task 1 — Backfill existing Qdrant points with `deleted_at_ts=0.0` (REVISION 1 — fixes B-4)

**File(s):** `infrastructure/scripts/backfill_qdrant_deleted_at.py` (CREATE)

**What:** Standalone Python script that connects to the live Qdrant instance, enumerates every xbrain collection (`memory_items` plus any others — discover via `client.get_collections()`), scrolls each collection's points in batches of 1000 using the Qdrant scroll API, and calls `client.set_payload(collection_name=..., payload={"deleted_at_ts": 0.0}, points=[id_batch])` for each batch. The script MUST be idempotent — re-running on already-tagged points is a no-op because `set_payload` overwrites with the same value.

Outline:

```python
"""Phase 11 — one-shot Qdrant backfill: set deleted_at_ts=0.0 on every existing point.

Run AFTER Task 2 (upsert writes the field) is deployed and BEFORE Task 3 (search filter)
merges to main. See plan 11-03 Section 1b for the deployment gate.

Idempotent: re-running on tagged points overwrites with the same value (no harm).
"""
import os
from qdrant_client import QdrantClient

QDRANT_URL = os.environ["QDRANT_URL"]                # e.g. http://qdrant:6333
QDRANT_API_KEY = os.environ.get("QDRANT_API_KEY")    # optional
BATCH = 1000
client = QdrantClient(url=QDRANT_URL, api_key=QDRANT_API_KEY)

collections = [c.name for c in client.get_collections().collections
               if c.name.startswith("memory_items") or c.name in {"facts"}]
# Adjust the filter above to your collection naming convention. If memory_items
# is the only Qdrant collection xbrain owns, keep just that.

for coll in collections:
    before_count = client.count(collection_name=coll, exact=True).count
    print(f"[backfill] {coll}: starting (count={before_count})")

    offset = None
    total = 0
    while True:
        points, offset = client.scroll(
            collection_name=coll,
            limit=BATCH,
            offset=offset,
            with_payload=False,
            with_vectors=False,
        )
        if not points:
            break
        ids = [p.id for p in points]
        client.set_payload(
            collection_name=coll,
            payload={"deleted_at_ts": 0.0},
            points=ids,
        )
        total += len(ids)
        print(f"[backfill] {coll}: tagged {total}/{before_count}")
        if offset is None:
            break

    after_count = client.count(collection_name=coll, exact=True).count
    assert before_count == after_count, (
        f"[backfill] FAIL: {coll}: before_count={before_count} != after_count={after_count}"
    )
    print(f"[backfill] OK: before_count={before_count} == after_count={after_count}")

print("[backfill] DONE")
```

The deployment runbook (operator side):

```bash
# From the VM, with QDRANT_URL pointing at the prod Qdrant:
docker exec -it xbrain-memory-api python /app/infrastructure/scripts/backfill_qdrant_deleted_at.py
# OR copy the script into the memory-api image's PYTHONPATH and invoke similarly.
```

**Why:** Without backfill, Task 3's `Range(lte=0.0)` filter excludes every legacy point because Qdrant range filters do NOT match points lacking the payload field (RESEARCH §Q3 Critical Pitfall — confirmed). Pre-Phase-11 memory content would silently vanish from `/v1/memory/search` results the moment the filter ships.

**Acceptance:**
1. Script runs to completion without exception.
2. For every collection processed, log shows `before_count == after_count`.
3. Post-run validation: `client.count(collection_name=coll, count_filter=Filter(must=[FieldCondition(key='deleted_at_ts', range=Range(gte=-1.0))]))` returns the same total as the collection size — proving every point now has the field.
4. Re-running the script is a no-op (no errors, same `before_count == after_count` line).

**Commit message:** `chore(infra): backfill Qdrant deleted_at_ts=0.0 on existing points`

**Risk acknowledgment:** On a >100k-point Qdrant index, the scroll loop can take 30-90s. Run off-peak. The script does not hold a transaction so it does not block writes — concurrent upserts during backfill will land with `deleted_at_ts=0.0` from Task 2 anyway.

### Task 3 — Filter soft-deleted points in `search()` + add mark_deleted/mark_restored helpers

**File(s):** `packages/memory-models/xbrain_memory/providers/native_provider.py`

> **REVISION 1 (B-4):** This task MUST NOT merge to main before Task 1 (backfill) has been run against the live Qdrant instance. The executor pauses between commit 2 (Task 2) and commit 3 (this task) to verify the backfill log line. See Section 1b.

**What:** Two changes in one commit (they touch the same file and ship together):

(a) In `search()` (around line 127–173): build the existing `must_conditions` list, then **also** append a `must_not` clause that excludes points where `deleted_at_ts > 0`. The qdrant-client 1.17.1 API:

```python
from qdrant_client.http.models import Filter, FieldCondition, Range

# Append to the outer must list:
must_conditions.append(
    FieldCondition(key="deleted_at_ts", range=Range(lte=0.0))
)
# OR equivalently as a top-level must_not:
qdrant_filter = Filter(must=must_conditions, must_not=[FieldCondition(key="deleted_at_ts", range=Range(gt=0.0))])
```

Use whichever the existing code patterns; the `lte=0.0` approach merges cleanly into existing `must` lists.

(b) Add two new public methods to `NativeProvider`:

```python
async def mark_deleted(self, item_id: UUID, deleted_at: datetime) -> None:
    """Flip the Qdrant payload deleted_at_ts to deleted_at.timestamp() for this point."""
    self._qdrant.set_payload(
        collection_name=self.collection_name,
        payload={"deleted_at_ts": deleted_at.timestamp()},
        points=[str(item_id)],
    )

async def mark_restored(self, item_id: UUID) -> None:
    """Reset Qdrant payload deleted_at_ts to 0.0 for this point."""
    self._qdrant.set_payload(
        collection_name=self.collection_name,
        payload={"deleted_at_ts": 0.0},
        points=[str(item_id)],
    )
```

These run synchronously inside an async method because the Qdrant Python client is sync; wrap with `asyncio.to_thread` if blocking event loop matters at scale. Use existing client patterns from the file as the style guide.

**Why:** BMO-05 (DELETE soft) and BMO-06 (restore) need a Qdrant-side flip so semantic search hides the point. Without this, the PG soft-delete is masked by a stale Qdrant payload.

**Acceptance:** `pytest packages/memory-models/tests/test_native_provider_soft_delete.py -v` (created in Task 4) PASS. Manual smoke from memory-api shell: upsert two test memory_items, call `mark_deleted(id_1, now())`, then `search(query='test', team_scope='default', limit=10)` returns only the non-deleted item. **Additional acceptance specifically for the backfill gate:** before merging, confirm `/v1/memory/search` against the live VM still returns at least one pre-Phase-11 result (i.e., backfill worked and the filter doesn't blackhole legacy content).

**Commit message:** `feat(memory-models): NativeProvider mark_deleted/mark_restored + soft-delete search filter`

## Section 4 — Risks + Mitigations

- **Risk: qdrant-client `Range` API drift.** Mitigation: pin to v1.17.1 (CLAUDE.md). If the API changes in a future bump, the integration test catches it immediately. Document the version assumption in the file docstring.
- **Risk: backfill takes >90s on production-sized indexes.** Mitigation: run off-peak; the script is idempotent so an interrupted run is safe to resume. Monitor the log — each batch prints progress.
- **Risk: `set_payload` is sync and blocks event loop.** Mitigation: wrap with `await asyncio.to_thread(self._qdrant.set_payload, ...)` if profiling shows it. For Phase 11 traffic levels (admin-driven UI), direct calls are fine.
- **Risk: `mark_deleted` called for an `entity_type` other than memory_item (e.g., contact, task).** Mitigation: contacts/tasks/etc. have NO Qdrant points. The endpoint in 11-05 must only call `mark_deleted` when `entity_type == 'memory_item'`. Document explicitly.
- **Risk: backfill script run BEFORE Task 2 ships.** Mitigation: the deployment runbook in Section 1b is explicit about ordering. A premature run is harmless (sets the field to 0.0 on existing points; new upserts after Task 2 ships will land with the same value).

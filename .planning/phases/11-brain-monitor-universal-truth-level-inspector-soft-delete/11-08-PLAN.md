# Plan 11-08 — app-site `/account/teams/brain/` UI

## Section 1 — Goal

Ship the user-facing Brain Monitor page on `app-site` (Firebase Hosting): a vanilla-JS single-page view at `https://app.example.com/account/teams/brain/?team=<slug>` that lists `GET /v1/brain/events`, lets admins/authors edit `truth_level` inline, soft-delete + restore items, toggle a "Show deleted" filter, and polls every 30 seconds for new rows. Matches the existing `account/teams/index.html` shell (no framework, no bundler, dark theme, JetBrains Mono). Satisfies BMO-09 + Success Criteria 1–3.

After this plan: a logged-in team member opens the URL, sees a paginated feed of all brain events for the team, can filter by entity_type/truth_level/source, edit truth_level inline via dropdown, and soft-delete/restore items. Polling **prepends** new rows at the top every 30s without page reload, preserving the user's scroll position and any rows already loaded via pagination.

## Section 2 — Files touched

- `app-site/account/teams/brain/index.html` — CREATE — main page (auth shell + filter panel + table + dropdown templates). Copy structural layout from `app-site/account/teams/index.html`.
- `app-site/account/teams/brain/brain.js` — CREATE — state + API client + DOM render + polling. Mirror patterns from `app-site/account/teams/teams.js`.
- `app-site/css/brain.css` — CREATE (or inline in index.html) — table layout, filter sidebar, truth-level dropdown styling. Reuse existing `--bg`, `--accent`, `--border` variables.
- `app-site/firebase.json` — VERIFY — confirm empty `rewrites` array still works (the page is at a real path `account/teams/brain/index.html` so no rewrite needed). No edit expected.

**URL scheme decision (resolves RESEARCH Open Question #2):**
- The route is `app-site/account/teams/brain/index.html` (real static path).
- Team slug is read from URL query string `?team=<slug>` (e.g., `https://app.example.com/account/teams/brain/?team=your-github-org`).
- This matches the existing flat-directory pattern in `app-site/account/teams/` and requires no `firebase.json` rewrite.
- The "[slug]" notation in CONTEXT.md is conceptual, not a literal Next.js-style dynamic route.

### Task 2 — Brain.js state, API client, render loop, inline edit, soft-delete (REVISION 1 — fixes M-2 + M-5)

**File(s):** `app-site/account/teams/brain/brain.js`

**What:** Mirror `teams.js` structure:

```js
const MEMORY_API_BASE = "https://api.example.com";
const TEAM_SLUG = new URLSearchParams(location.search).get("team");
const TRUTH_LEVELS = ["EPHEMERAL","WORKING","VALIDATED","CANONICAL","PUBLIC"];

const state = {
  xbt: localStorage.getItem("xbrain_xbt_token"),  // already minted by teams.js or onboarding
  items: [],
  nextCursor: null,
  filters: { entity_type: [], truth_level: [], source: "", created_by: "", since: null, include_deleted: false },
  loading: false,
  pollTimer: null,
  activeEditRowId: null,   // suppress re-render of a row the user is editing
  currentUserId: null,    // populated from /v1/me
  membership: null,        // {role: 'admin'|'member'}
};
```

Functions to implement:

- **`loadEvents({ append, cursor })`** — `GET /v1/brain/events?...` with filter query string + Authorization Bearer header + `X-Team-Scope: ${TEAM_SLUG}`. `append=true` → push to `state.items`; `append=false` (first load or filter change) → replace `state.items`. Sets `state.nextCursor`. **NOTE: this function is for filter-driven loads and pagination, NOT for live polling.** Polling uses `pollForNewItems()` below.

- **`pollForNewItems()`** (REVISION 1 — M-2) — dedicated function for the 30s live feed. Computes `since = state.items[0]?.created_at` (newest seen, ISO 8601), then fires:
  ```
  GET /v1/brain/events?since={since_iso}&limit=50
    + all currently active filters from state.filters (so the live feed honors the same filter set as the original query)
  ```
  Returns ONLY events with `created_at > since`. The function **prepends** the response items to `state.items` (`state.items = [...response.items, ...state.items]`) and re-renders. Existing rows are untouched. The user's pagination cursor (`state.nextCursor`) is left untouched — `pollForNewItems` does NOT replace state, does NOT reset the cursor, does NOT call `loadEvents`.

  Rows the user is currently editing (`activeEditRowId === item.id`) are NOT re-rendered (skip them in the render loop) — the new prepend just inserts new rows at the top without touching the edit-in-progress row's DOM.

- **`renderTable()`** — generates `<tr>` per item with `<select class="truth-level">` (the dropdown is disabled if user can't edit — see canEdit() below). When re-rendering after a `pollForNewItems` prepend, only inserts new `<tr>` elements for the prepended items; does not destroy/recreate existing rows. Practically: maintain a `Map<entity_id, HTMLTableRowElement>` and on render, diff against `state.items` to compute additions only.

- **`canEdit(item)`** — returns true if `state.membership.role === 'admin'` OR `item.created_by === state.currentUserId`.

- **`patchTruthLevel(item, newValue)`** — optimistic UI: replace row immediately, fire `PATCH /v1/brain/events/{entity_type}/{entity_id}` with body `{truth_level: newValue}`. On 200 keep; on 4xx rollback to the previous value AND show a toast. **403 handling (REVISION 1 — M-5):** if response status is 403, show the toast `"You can only edit items you created. Contact a team admin to modify items created by others."` (exact wording — mirrors the 403 detail body the API returns from `assert_can_edit_brain_event`). Other 4xx statuses get the generic toast `"Failed to update truth level"`. On 5xx show `"Server error — please retry"`.

  Implementation:
  ```js
  if (response.status === 403) {
    showToast("You can only edit items you created. Contact a team admin to modify items created by others.");
  } else if (!response.ok) {
    showToast("Failed to update truth level");
  }
  ```

- **`softDelete(item)`** — confirmation modal "This will be purged permanently in 30 days unless restored." (the warning copy from CONTEXT.md). On confirm, `DELETE /v1/brain/events/{entity_type}/{entity_id}`. On 204 remove the row (or fade if "Show deleted" is on); on 403 show the M-5 toast above; on other error generic toast.

- **`restoreItem(item)`** — `POST /v1/brain/events/{entity_type}/{entity_id}/restore`. On 200 un-fade; on 410 toast `"Retention window expired — item cannot be restored"`; on 403 show the M-5 toast.

- **`startPolling()`** (REVISION 1 — M-2) — `state.pollTimer = setInterval(pollForNewItems, 30_000)`. Does NOT call `loadEvents`. Does NOT replace state. Does NOT reset the cursor.

- **`setupIntersectionObserver()`** — when sentinel enters viewport, call `loadEvents({ append: true, cursor: state.nextCursor })`.

- **`init()`** — fetch `/v1/me` (for currentUserId) + `/v1/teams/my-teams` (for membership role), then `loadEvents({ append: false, cursor: null })` (initial load), then `startPolling()`.

- **Defensive dropdown gate (REVISION 1 — M-5):** when rendering a row where `canEdit(item) === false`, the `<select>` is rendered with `disabled` AND its `change` event handler is NOT attached (event delegation skips disabled selects). This prevents a user from re-enabling the `disabled` attribute via DevTools and bypassing the UI guard — the change handler simply doesn't exist for non-editable rows. Implementation: in the event-delegation handler, check `if (!canEdit(item)) return;` as the first line, AND the rendered `<select>` is `<select disabled>` for visual clarity.

The dropdown change handler uses event delegation on the table body. The dropdown options list = the 5 truth levels. Inline edit fires PATCH immediately on `change` event.

Bulk select: a `<input type="checkbox" class="bulk-select">` per row + a header checkbox. Only visible if `state.membership.role === 'admin'`. "Set truth_level to X" bulk action calls PATCH in a loop with concurrency 4. "Delete selected" calls DELETE in a loop. Errors aggregated in a single toast at end (collect failures and show single toast "5/10 succeeded, 5 failed: <list of errors>").

**Why:** BMO-09 + Success Criteria 1, 2, 3. Inline edit + soft-delete + restore + polling are the user-visible payoff of Phase 11. The since-based prepend semantics match the live-feed UX the user expects (new rows at top, no scroll loss, no data destruction).

**Acceptance:** Manual UAT (covered in 11-09):
- Page loads with rows.
- Change a row's truth_level dropdown → PATCH fires, row stays updated after refresh.
- **403 path:** as a non-author non-admin, attempt to PATCH (via DevTools manipulation if dropdown disabled): toast shows the exact M-5 wording.
- Click delete → row disappears, reappears with "Show deleted" toggle, restore brings it back.
- **Polling correctness (M-2):** open monitor at T=0 with rows visible, insert a new task at T=15s via API/agent. At T=30s the new row appears at the TOP of the list. Existing rows remain unchanged. Scroll position preserved. `state.nextCursor` unchanged.
- **Polling with filter:** apply filter `entity_type=task`. Insert a memory_item via API. After 30s, new memory_item does NOT appear (filter excludes it). Insert a task → appears at top.
- Non-admin non-author sees disabled dropdown + hidden delete button on rows they didn't create. Attempting to bypass via DevTools fires no PATCH (the change handler short-circuits on `!canEdit`).

**Commit message:** `feat(app-site): brain monitor JS — state, since-prepend polling, inline edit, soft-delete with 403 toast`

## Section 4 — Risks + Mitigations

- **Risk: CORS preflight failure on PATCH/DELETE from `app.example.com` → `api.example.com`.** Mitigation: the existing app-site already calls `/v1/me/api-token` and `/v1/teams/my-teams` with `Authorization` + custom `X-Team-Scope` header — CORS is already configured. New verbs PATCH/POST/DELETE must be in the nginx/memory-api `Access-Control-Allow-Methods` list. Verify with a manual `curl -X OPTIONS -H 'Origin: https://app.example.com' -H 'Access-Control-Request-Method: PATCH' https://api.example.com/v1/brain/events/task/$(uuidgen)` — expect 204 with the right headers.
- **Risk: polling fires while user is editing dropdown.** Mitigation: `activeEditRowId` tracks the currently edited row; the prepend-only render does NOT touch that row's DOM. New rows still prepend; existing rows untouched.
- **Risk: bulk operations partial failure UX.** Mitigation: collect failures and show single toast "5/10 succeeded, 5 failed: <list of errors>". Don't crash, don't retry automatically.
- **Risk: no test infrastructure for the frontend.** Mitigation: rely on manual UAT (script in 11-09 with playwright-mcp if needed). DO NOT plan an automated frontend test — the project has no test runner for app-site. Add a note to plan 11-09 that UAT is the verification.
- **Risk: 1000+ row table sluggish without virtualization.** Mitigation: IntersectionObserver pagination keeps DOM under 200 rows for typical browsing. If row count grows beyond 5000, a future plan can swap in a virtual-scroll library; for now, pagination is sufficient (RESEARCH §Q6 confirms acceptable at current xbrain scale).
- **Risk: `since` cursor on poll skips a row inserted at exactly the same `created_at` as the newest seen.** Mitigation: server filter is `created_at > since` (strict greater-than), so a tie-equal row inserted in the same microsecond is missed. In practice this requires sub-microsecond simultaneity; acceptable for Phase 11. A future improvement can use the tuple `(created_at, entity_type, entity_id)` cursor for polling too.

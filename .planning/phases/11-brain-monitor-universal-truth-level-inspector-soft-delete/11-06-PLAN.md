# Plan 11-06 — Add `deleted_at IS NULL` to all existing read paths

## Section 1 — Goal

Patch the six existing read paths flagged in RESEARCH §Q8 so soft-deleted rows disappear from default API responses without changing the client contract. Without this plan, BMO-05 (DELETE soft) appears to "work" but soft-deleted rows continue to surface in `/v1/tasks`, `/v1/crm/contacts`, `/v1/memory/search` post-fetch hydration, `/v1/conversations`, and `/v1/messages` — making the entire soft-delete mechanism useless.

After this plan: every existing list/search endpoint excludes `deleted_at IS NOT NULL` rows. Regression test per router confirms.

## Section 2 — Files touched

- `apps/memory-api/app/routes/tasks.py` — MODIFY — add `AND deleted_at IS NULL` to `list_tasks` and `get_task` queries.
- `apps/memory-api/app/routes/crm.py` — MODIFY — same for `list_contacts` and `get_contact`.
- `apps/memory-api/app/routes/conversations.py` — MODIFY — same for any list endpoint reading `conversations`. (Verify the actual query path; the file may delegate to a repo function.)
- `apps/memory-api/app/routes/messages.py` — MODIFY — add `AND deleted_at IS NULL` to every SELECT against the `messages` table on GET endpoints. (REVISION 1 — fixes B-3.)
- `apps/memory-api/app/repos/messages.py` — MODIFY — if `routes/messages.py` delegates to this repo, patch the SQL here instead (RESEARCH §Q8 flagged this path; executor verifies the actual delegation pattern before editing).
- `packages/memory-models/xbrain_memory/providers/native_provider.py` — MODIFY — in the PG hydration step of `search()` (the `SELECT * FROM memory_items WHERE id = ANY(...)` line), add `AND deleted_at IS NULL`.
- `apps/memory-api/tests/test_soft_delete_regression.py` — CREATE — pytest verifying each patched router returns N-1 rows after soft-deleting one.

**Note on routes already filtered:** `repos/team_messages.py` already filters `deleted_at IS None` per RESEARCH §Q8. No change needed there — but the regression test should include team_messages to lock that behavior.

## Section 3 — Tasks

### Task 1 — Patch tasks + crm + conversations + messages routes (REVISION 1 — fixes B-3)

**File(s):** `apps/memory-api/app/routes/tasks.py`, `apps/memory-api/app/routes/crm.py`, `apps/memory-api/app/routes/conversations.py`, `apps/memory-api/app/routes/messages.py`, `apps/memory-api/app/repos/messages.py` (if the route delegates here)

**What:** In each file, locate every GET-endpoint SQL string that reads from the entity table and add `AND deleted_at IS NULL` to the WHERE clause. Example for `tasks.py` line 97:

```python
sql = "SELECT * FROM tasks WHERE team_scope = :ts AND deleted_at IS NULL"
```

For `get_task` line 124:
```python
sa.text("SELECT * FROM tasks WHERE id = :id AND team_scope = :ts AND deleted_at IS NULL")
```

Repeat the same pattern for:

| File | Endpoints | Pattern |
|------|-----------|---------|
| `crm.py` | `list_contacts` (~line 74), `get_contact` (~line 92) | `... FROM contacts WHERE team_scope = :ts AND deleted_at IS NULL` |
| `conversations.py` | any list/get endpoint reading `conversations` | `... FROM conversations WHERE ... AND deleted_at IS NULL` |
| `messages.py` | every GET endpoint (e.g., `list_messages_by_conversation`, `get_message`) | `... FROM messages WHERE conversation_id = :cid AND deleted_at IS NULL` (or `WHERE id = :id AND deleted_at IS NULL` for single-row reads) |
| `repos/messages.py` | every SELECT-style helper returning messages | for new queries: `WHERE deleted_at IS NULL`; for existing WHERE clauses: append `AND deleted_at IS NULL` |

**Universal rule for the `messages` table:** every SELECT against `messages` from a GET path must add the filter. PATCH/DELETE/restore paths in the brain router intentionally DO NOT filter (the brain monitor needs to see soft-deleted rows).

**DO NOT** add this filter to PATCH/DELETE endpoints — the brain monitor's DELETE/restore needs to see soft-deleted rows.

For `conversations.py` and `messages.py`: read the file first to find the exact query path. If a route file delegates to a repo (e.g., `routes/messages.py` → `repos/messages.py`), patch the repo function instead. Confirm the call chain with `grep -rn "FROM messages" apps/memory-api/app/` before editing.

**Why:** BMO-07. Single grep gate ensures no read path leaks soft-deleted rows. RESEARCH §Q8 explicitly listed `messages.py` as "Likely missing, MEDIUM risk" — addressing it now closes the regression surface.

**Acceptance:**

```bash
# Hygiene: every SELECT from these tables in route/repo files must filter deleted_at.
grep -rn "FROM tasks WHERE" apps/memory-api/app/routes/tasks.py | grep -v "deleted_at IS NULL" || echo "OK tasks.py"
grep -rn "FROM contacts WHERE" apps/memory-api/app/routes/crm.py | grep -v "deleted_at IS NULL" || echo "OK crm.py"
grep -rn "FROM conversations WHERE" apps/memory-api/app/routes/conversations.py | grep -v "deleted_at IS NULL" || echo "OK conversations.py"
grep -rn "FROM messages WHERE" apps/memory-api/app/routes/messages.py apps/memory-api/app/repos/messages.py | grep -v "deleted_at IS NULL" || echo "OK messages*"
```

Each line should print `OK <file>` (meaning no unfiltered SELECTs remain). End-to-end check after deploy: insert a task, soft-delete it via DB UPDATE, `curl /v1/tasks` returns the task list without it. Repeat for `curl /v1/messages?conversation_id=...`. Regression test in Task 3 codifies this.

**Commit message:** `fix(memory-api): exclude soft-deleted rows from tasks/crm/conversations/messages list endpoints`

### Task 2 — Patch NativeProvider search PG hydration

**File(s):** `packages/memory-models/xbrain_memory/providers/native_provider.py`

**What:** In `search()`, after Qdrant returns matched point IDs (~line 160), the provider issues a second query like `SELECT * FROM memory_items WHERE id = ANY(:ids)` to hydrate full rows. Add `AND deleted_at IS NULL` to this clause:

```python
hydrate_sql = "SELECT * FROM memory_items WHERE id = ANY(:ids) AND deleted_at IS NULL"
```

This is the **second layer of defense** mentioned in RESEARCH PITFALL — even if a Qdrant point's `deleted_at_ts` payload is stale (e.g., older points not yet backfilled in 11-03), the PG filter cuts the row from results. Belt and suspenders.

**Why:** Qdrant `Range` filter excludes most cases; this PG filter handles the residual.

**Acceptance:** With one memory_item soft-deleted in PG (`deleted_at = now()`) but Qdrant payload still `deleted_at_ts = 0.0`, `POST /v1/memory/search` does NOT return that row. Verified by the regression test.

**Commit message:** `fix(memory-models): exclude deleted memory_items from native_provider search hydration`

### Task 3 — Regression test per affected router (REVISION 1 — adds messages.py coverage)

**File(s):** `apps/memory-api/tests/test_soft_delete_regression.py`

**What:** Pytest fixture seeds two rows per table (tasks, contacts, conversations, messages, memory_items, team_messages). Soft-delete one of each via direct DB UPDATE (`UPDATE tasks SET deleted_at = now() WHERE id = :id`). Then make the corresponding API call and assert N-1 rows returned (where N was the seed count). Cases:

1. `GET /v1/tasks` → 1 row (the non-deleted one).
2. `GET /v1/tasks/{deleted_id}` → 404.
3. `GET /v1/crm/contacts` → 1 row.
4. `GET /v1/crm/contacts/{deleted_id}` → 404.
5. `GET /v1/teams/{team_id}/messages` → 1 row (this path already filtered; locks behavior).
6. **`GET /v1/messages?conversation_id=<id>`** — seed 1 normal + 1 soft-deleted message in the same conversation; endpoint returns only the normal one. (REVISION 1 — covers B-3.)
7. **`GET /v1/messages/{deleted_id}`** (or whichever single-row endpoint exists) → 404.
8. `POST /v1/memory/search` (vector search) → only the non-deleted item returned. May require mocking or local Qdrant — use `pytest.mark.integration` and skip if Qdrant unavailable.
9. (Negative) `GET /v1/brain/events` with `include_deleted=true` → 2 rows (both visible). This ensures the brain monitor itself remains opt-in to deleted view.

If `routes/messages.py` exposes a different path or shape than assumed, adjust cases 6+7 to match the actual route signature (e.g., `/v1/conversations/{cid}/messages` if that's the convention). Discover via `grep -n "@router" apps/memory-api/app/routes/messages.py`.

**Why:** Locks the contract. Any future regression that drops the `deleted_at IS NULL` filter goes red here.

**Acceptance:** `pytest tests/test_soft_delete_regression.py -v` → 9 PASS (8 if Qdrant skipped).

**Commit message:** `test(memory-api): soft-delete regression — all read paths exclude deleted rows (incl. messages)`

- **Risk: `routes/messages.py` delegates to `repos/messages.py` and the route file has no SQL.** Mitigation: Task 1 covers both files; the grep gate in acceptance catches whichever one holds the SQL.

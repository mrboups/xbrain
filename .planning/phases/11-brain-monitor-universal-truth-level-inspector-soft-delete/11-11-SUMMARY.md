# Phase 11 Plan 11-11: Superadmin Dashboard UI Summary

**One-liner:** Ship a vanilla-JS superadmin dashboard at `/account/admin/` that consumes the 5 cross-team `/v1/admin/brain/*` endpoints from plan 11-10, with inline SVG sparklines (no chart deps) and a one-click drill-down into any team's brain monitor that toggles a logged-access banner + routes reads through the audited admin endpoint.

## Goal Achieved

A signed-in superadmin can open `https://app.grooveos.app/account/admin/` and see four sections live within 1 GET round-trip:

1. **Brain Overview** — counts × entity_type matrix per team, hover-tooltip showing the per-`truth_level` breakdown.
2. **Storage** — PG rows (with per-table tooltip) + Qdrant points + MinIO bytes (human-formatted), with a totals row that excludes `N/A` cells and flags them with a footnote.
3. **Activity** — 30-day events/day inline SVG sparkline per team with per-point hover tooltips (date + count) and screen-reader-friendly aria-labels.
4. **Top Sources** — top-5 source columns picked dynamically across all teams + an "other" bucket, with row + grand totals.

A non-superadmin lands on the page → the probe (`GET /v1/admin/brain/overview`) returns 403 → the "Access denied" fallback panel renders and **no other fetches fire**. No data leak path exists in the client because the gate is server-side.

Clicking **Drill down →** on any team row navigates to `/account/teams/brain/?team=<slug>&as_superadmin=1`, which:
- Renders the yellow "Viewing as superadmin — this access is logged." banner (role=status, aria-live=polite).
- Routes both the initial load AND every 30-second poll cycle through `/v1/admin/brain/events?team_slug=<slug>` (audit row written server-side on every call, satisfying SC-9).
- Hides every inline truth-level dropdown, Delete and Restore button, and bulk-action bar (read-only v1 — admin write endpoints are deferred to Phase 12+).

## Key Decisions

### 1. Probe-and-403 superadmin detection (over a new `/v1/me { is_superadmin }` field)

Rationale:
1. Zero backend change required.
2. The probe IS the first data fetch — its response is cached into `state.overview` and reused by `renderOverview()`. Happy path = 1 round-trip, not 2.
3. Failure modes are explicit (`403` → fallback; any other error → error panel with reason).
4. Forward-compatible: a future `/v1/me` flag still works as a fallback path; the probe is the authoritative gate either way (the API is the truth).

### 2. Drill-down is READ-ONLY in v1

The plan locked admin write endpoints (PATCH/DELETE/restore admin variants) to Phase 12+. So in `brain.js`:
- `canEdit()` short-circuits to `false` when `IS_SUPERADMIN_VIEW === true` — every Delete/Restore button vanishes, every truth-level dropdown is disabled. Even items the superadmin happens to have authored themselves remain read-only.
- `state.membership` is forced to `{role: "viewer", team_id: null}` after the membership load — bulk-action UI never appears.

Belt-and-braces: even if the UI were tampered with, the server-side PATCH/DELETE endpoints from 11-04/11-05 are team-scoped and would return 403 for a non-member superadmin.

### 3. `brainEventsPath(qs)` endpoint substitution helper

Both call sites (`loadEvents` + `pollForNewItems`) route through a single helper:

| View | Endpoint | Header |
|------|----------|--------|
| Default team-scoped | `GET /v1/brain/events?<qs>` | `X-Team-Scope: <slug>` |
| `?as_superadmin=1` | `GET /v1/admin/brain/events?team_slug=<slug>&<qs>` | `Authorization` only (admin endpoint bypasses `get_team_scope`) |

The 30-second polling cadence is **preserved** in superadmin view — every poll writes a fresh `audit_log` row server-side (matches verify-phase11.sh assertion 15 expectation that any drill-down session correlates 1:1 with `audit_log` rows of `action='superadmin_brain_access'`).

The new `skipTeamScope: true` opt-in on `xbtFetch` is the minimal blast radius — every other caller still passes `X-Team-Scope` exactly as before.

### 4. 403 routing distinguishes elevation failure from outage

When the admin endpoint returns 403 in superadmin view, `loadEvents` now surfaces:

> "You are not a superadmin. The admin endpoint refused this request."

…instead of the generic "Failed to load events". This distinguishes a true elevation failure (operator opens the URL but isn't on `ADMIN_USER_SUBS`) from a transient server outage — the operator can immediately tell which.

### 5. Inline SVG sparkline (no Chart.js / D3)

Per CONTEXT.md, no chart library may be added. `sparkline.js` is 86 lines of vanilla SVG:
- `<polyline>` + per-point `<circle>` elements.
- Each `<circle>` carries a `<title>` for hover tooltips (date + count).
- The parent `<svg>` carries `role="img"` + `aria-label` summarising total events + peak day (e.g. "Activity sparkline: 142 events over 30 days, peak 17 on 2026-05-12") — screen readers get a meaningful summary instead of nothing.
- `viewBox` + `preserveAspectRatio="none"` lets the SVG flex if the table cell ever resizes.
- `max=1` floor avoids divide-by-zero when every day is 0.
- Colour driven by CSS `currentColor` — themable without rewriting the renderer.

### 6. Dynamic column discovery

- **Overview** — `entity_type` columns are derived from `Object.keys(team.counts)` across all teams, sorted alphabetically. If a future migration adds an arm to `v_brain_events`, the matrix expands automatically with no UI edit.
- **Top Sources** — source-label columns come from the response, not a hardcoded `[librechat, owui, granola, agent, api]` list. Top-5 by global count + an "other" bucket lumps the long tail.

### 7. Vertical card layout (over tabs/accordions)

V1 stacks the 4 sections vertically — simpler scroll, no JS state for "active tab". Phase 12 can layer tabs on top if the section count grows.

### 8. `.firebase/hosting..cache` committed

Mirrors plan 11-08's ship commit (`1484731`). The cache is a tiny CSV that Firebase regenerates on every deploy; committing it keeps the worktree clean and lets `git status` reliably detect uncommitted local changes.

## Deviations from Plan

**Adjustment to the plan's localStorage key constant.** The plan's Task 1 spec used `localStorage.getItem("xbrain_xbt_token")` in its example, but `brain.js` (11-08) standardised on `xbt_token` as the canonical key with `xbrain_xbt_token` as a read-only legacy fallback. `admin.js` follows the canonical convention to avoid an auth break for any user landing on `/account/admin/` after `teams.js` migrated their token. The legacy fallback is read; the canonical key is written.

Categorisation: **[Rule 1 — Bug]** — using a non-canonical key would silently break sign-in for any user who'd previously visited `/account/teams/` (which is the only path that mints the token in the first place).

No other deviations. All 7 tasks executed exactly as written.

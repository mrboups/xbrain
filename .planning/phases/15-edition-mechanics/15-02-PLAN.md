## THE ROUTER CLASSIFICATION — resolved, with reasoning. Use this table verbatim.

`app/main.py` mounts **35** routers. Research flagged classification as its one LOW-confidence area, so
here is the resolution and *why*, so no executor re-litigates it.

**The governing fact:** locked decision **Q6 / D-15-01** dropped the paid tier, the Ed25519 license and
requirement EDIT-03. **Nothing in the product is paywalled.** The only closed surface is the *hosted
control plane* — billing, multi-tenant provisioning, trial caps. So the question is never "is this
feature premium?" (no feature is). It is only: **"is this router meaningless without the hosted control
plane?"** Almost nothing is.

**The default is CORE.** We fail *open* on features and never on data isolation: a self-hoster who
loses a capability they should have had is a silent product regression they cannot debug; a SaaS-only
route accidentally mounted in an OSS install is inert (it has no hosted backend, no billing table, no
Resend key). The two SaaS routers below are the total enumerable leak surface, and the negative test in
Task 3 pins them.

### SAAS-ONLY — exactly 2 routers

| Router | Path(s) | Why SaaS-only |
|---|---|---|
| `waitlist` | `POST /v1/waitlist` | Docstring: *"proxy Resend email signup, no auth required."* It exists to serve the **hosted landing page's** signup form; it needs `RESEND_API_KEY` and a marketing site. A self-hoster has no waitlist. Named verbatim in ROADMAP SC#2. |
| `external_sessions` | `GET/POST /v1/me/external-sessions`, `DELETE /v1/me/external-sessions/{provider}` | The Phase-9 session-bridge registry. Its only writer is the `session-bridge` container, which D-15-02 places in the `saas` profile. Named verbatim in ROADMAP SC#2 ("external_sessions/bridge routing"). |

The other two categories ROADMAP SC#2 names — **"multi-tenant admin"** and **"billing"** — have **no
router at all** today (confirmed by reading all 35 modules). There is nothing to gate. Do not invent one.

### CORE — the other 33 routers (always mounted, every edition)

`health, internal, internal_github, me, me_github, auth_github, teams, conversations, messages, audit,
media, memory, promotions, graph, system_prompt, admin_drive, admin_projects, crm, tasks, drive_webhook,
github_repos, granola_integration, agents, team_chat, brain, admin_brain, admin_wipe, webhooks_github`
(28) **+ the 5 unprefixed OAuth routers** `oauth_metadata, oauth_register, oauth_introspect,
oauth_authorize, oauth_token` (the Claude.ai / ChatGPT-web Custom Connector — ROADMAP SC#2 names the
"ChatGPT-web connector" as core explicitly).

Three of those deserve their reasoning stated, because a careless reader would gate them:

- **`crm` and `tasks`** — their module docstrings **literally say `(paid tier only — D1, D2)` /
  `(paid tier only — D4, D6)`**. That is a **stale comment from the cancelled license design.** The
  tier it refers to no longer exists (Q6). They shipped in Phase 7 as ordinary product features. They
  are **CORE**, and Task 2 fixes the docstrings so the next reader does not repeat this mistake.
- **The GitHub-auth family** (`internal_github, auth_github, me_github, github_repos,
  webhooks_github`) — **CORE**. A self-hoster can register their own GitHub App. These follow the
  *Neo4j precedent*: mounted always, functionally inert when unconfigured (empty `GITHUB_APP_*` →
  the endpoints error/no-op on their own). "Opt-in" here means opt-in by **config**, never by removing
  the route. Gating these would take sign-in away from a self-hoster who *did* configure a GitHub App —
  a functional regression versus today.
- **`admin_brain` / `admin_wipe` / `admin_projects`** — **CORE**. These are *single-install* superadmin
  surfaces (Brain Monitor, wipe, deploy registry). They are not the *multi-tenant, cross-customer*
  admin that SC#2 means by "multi-tenant admin". A self-hoster is the admin of their own install and
  needs them.

### The axis you must NOT conflate

`EDITION` is **oss vs saas**. It is *not* "is this integration configured". Neo4j / Drive / Granola /
GitHub availability is controlled by env-emptiness + compose profile (is the container reachable), and
those routers stay mounted and degrade — `graph.py` already `HTTPException(503, ...)`s when the driver
is `None`, and that is the correct, shipped pattern. Do not EDITION-gate a router because its backing
integration might be off.

### One coupling to document (not to fix here)

`session-bridge` (a `saas` compose service) POSTs to `/v1/me/external-sessions`. Therefore:
**if `COMPOSE_PROFILES` includes `saas`, `EDITION` must be `saas`** — otherwise session-bridge's
`register` frame gets a 404. That invariant is documented in `.env.example` by plan 15-03 and asserted
by the gate in 15-04. Nothing to implement here; just do not be surprised by it.

import pytest

import app.routes as routes_pkg
from app.config import Settings
from app.main import CORE_ROUTERS, SAAS_ONLY_ROUTERS, create_app

SAAS_ONLY_PATHS = ["/v1/waitlist", "/v1/me/external-sessions"]

CORE_PATHS = [
    "/v1/healthz",
    "/v1/media/upload",
    "/.well-known/oauth-authorization-server",  # ChatGPT/Claude.ai web connector — core, never gated

def _paths(edition: str) -> set[str]:
    return {r.path for r in create_app(edition).routes}


def test_oss_does_not_mount_saas_routers():
    oss = _paths("oss")
    for p in SAAS_ONLY_PATHS:
        assert p not in oss, f"LEAK: {p} is mounted under EDITION=oss"

    saas = _paths("saas")
    for p in SAAS_ONLY_PATHS:
        assert p in saas, f"{p} missing under EDITION=saas"

    for edition in ("oss", "saas"):
        paths = _paths(edition)
        for p in CORE_PATHS:
            assert p in paths, f"core route {p} missing under EDITION={edition}"

    classified = {id(r) for r, _, _ in [*CORE_ROUTERS, *SAAS_ONLY_ROUTERS]}

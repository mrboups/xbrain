## Environment facts (verified, not assumed)

- Docker Desktop 4.81.0, daemon up, `docker compose` **v5.2.0**.
- Host is **arm64** (`linux/aarch64`); prod is amd64.
- **DO NOT BUILD IMAGES.** An arm64 build is useless for the prod VM. Every check below either pulls a
  multi-arch upstream image or runs the real source inside a stock `python:3.12-slim` — the exact
  technique the Phase-15 research used to live-boot memory-api without a build.
- The **only** service in the whole compose file with no arm64 image is `xbrain-backup`
  (`google/cloud-sdk:slim` is amd64-only). It is isolated in the `ops` profile precisely so every other
  profile stays live-verifiable here. `ops` is therefore verified at the **config layer only** — say so
  in the output, do not fake a boot.
- **The Git-Bash mount trap (cost real time in Phase 14):** a host bind mount from Git Bash needs a
  Windows-style path AND `MSYS_NO_PATHCONV=1`. A POSIX `$PWD` path **silently fails to mount** — the
  container then runs against its own stock filesystem, every check passes, and the gate proves nothing.
  Task 3 therefore hard-guards the mount and **FAILS** (never SKIPs) if it did not land.

## Two things a naive gate would miss — the checker found both

1. **Count-based profile checks are not enough.** Tag `session-bridge` (spec: `saas`) as `integrations`
   and `mcp-calendar` (spec: `integrations`) as `saas`: the counts stay 14/7, `config --profiles` is
   unchanged, and every `--profile X config -q` still exits 0 (neither swap crosses a `depends_on` edge).
   A count-only gate reports PASS while an operator enabling `saas` gets **no `session-bridge`** —
   silently breaking the Pro/Max bridge and the only writer of `/v1/me/external-sessions`. **Assert every
   profile's membership BY NAME.**

2. **`COMPOSE_PROFILES=saas` + `EDITION=oss` (the default) is a silent 404 factory.** `session-bridge`
   POSTs `/v1/me/external-sessions`, which `EDITION=oss` does not mount. The register frame 404s and
   there is no other symptom anywhere. **This must be detected, not documented.**

   **Where the check goes, and why:** in `preflight-env.sh` (which `make deploy` already runs on every
   deploy) and asserted by this gate — **not** as a `field_validator` in memory-api. `COMPOSE_PROFILES`
   is an *orchestrator* concept; teaching the application to read it inverts the dependency (the app
   would refuse to boot based on a variable that means nothing outside Compose, and would break anyone
   running memory-api standalone with `COMPOSE_PROFILES` merely exported in their shell). The ops layer
   is where the two knobs are chosen, so the ops layer is where their consistency is enforced — and
   `preflight-env.sh` runs on the real deploy path, not just when someone remembers to run the gate.

Both scripts ship to self-hosters: **do not hardcode any production domain or maintainer-specific host.**

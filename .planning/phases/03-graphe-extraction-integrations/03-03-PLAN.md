**Section 1 — Contexte**
- Expliquer pourquoi les scopes sont nécessaires (drive-sync, mcp-drive-read, mcp-calendar)
- Confirmer que les utilisateurs existants sans besoin Drive/Calendar ne voient pas de re-consentement (incremental auth)

**Section 2 — Scopes à ajouter dans Google Cloud Console**
Lister les 3 scopes avec leur classification Google et leur usage dans xbrain :
- `https://www.googleapis.com/auth/drive.readonly` — Drive sync (drive-sync service) + live read (mcp-drive-read tool). Classification: Sensitive scope — requires OAuth verification if app >100 users or is published externally. Pour usage interne, pas de vérification requise.
- `https://www.googleapis.com/auth/drive.file` — Write-back vers Drive (INT-03, opt-in explicite uniquement). Ne pas ajouter au consentement initial — demander séparément lors de l'opt-in write-back.
- `https://www.googleapis.com/auth/calendar.readonly` — Calendrier Google Calendar (mcp-calendar tool). Classification: Sensitive scope — même règle que drive.readonly.

**Section 3 — Étapes dans Google Cloud Console**
Instructions pas-à-pas :
1. Console GCP → projet xbrain → "APIs & Services" → "OAuth consent screen"
2. Cliquer "EDIT APP" → section "Scopes" → "+ ADD OR REMOVE SCOPES"
3. Ajouter `drive.readonly` et `calendar.readonly` (PAS `drive.file` à cette étape)
4. Sauvegarder et publier (si l'app est en mode "Testing", les scopes ne fonctionnent que pour les test users)
5. Vérifier que les 2 scopes apparaissent dans la liste "Non-sensitive scopes" ou "Sensitive scopes" selon leur classification

**Section 4 — Variables d'environnement à ajouter dans .env**
```bash
# Google OAuth — credentials existants (ne pas changer)
# GOOGLE_CLIENT_ID=...  (existant)
# GOOGLE_CLIENT_SECRET=...  (existant)

# Google OAuth — ajouts Phase 3
# Ces scopes sont demandés lors du flow d'incremental auth (drive-sync setup + calendar setup)
GOOGLE_DRIVE_READONLY_SCOPE=https://www.googleapis.com/auth/drive.readonly
GOOGLE_CALENDAR_READONLY_SCOPE=https://www.googleapis.com/auth/calendar.readonly
GOOGLE_DRIVE_FILE_SCOPE=https://www.googleapis.com/auth/drive.file
# Encryption key for OAuth credentials stored in team_drive_mappings.oauth_credentials_enc
# Generate: python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
OAUTH_CREDENTIALS_ENCRYPTION_KEY=__FILL_FERNET_KEY__
```

**Section 5 — Flow d'incremental auth (implémenté par drive-sync setup)**
Décrire le flow que l'admin configure pour les utilisateurs :
- Trigger : admin mappe un dossier Drive via `POST /v1/admin/drive-mapping`
- Response : memory-api retourne un `authorization_url` Google avec paramètres :
  - `scope`: existing_scopes + `drive.readonly`
  - `include_granted_scopes=true` (scopes déjà accordés restent valides)
  - `access_type=offline` (refresh_token dans la réponse)
  - `prompt=consent` (force l'affichage même si scopes partiellement accordés)
- Après consentement : memory-api reçoit le code, échange contre access_token + refresh_token, chiffre les credentials avec `OAUTH_CREDENTIALS_ENCRYPTION_KEY`, stocke dans `team_drive_mappings.oauth_credentials_enc`

**Section 6 — Séparation drive.readonly vs drive.file**
- `drive.readonly` : demandé lors du setup de sync. L'utilisateur voit "Voir et télécharger tous vos fichiers Google Drive".
- `drive.file` : demandé UNIQUEMENT lors d'une action write-back explicite (l'utilisateur dit "Écrire ce résumé dans Drive"). Ne jamais bundler avec le consentement initial — consent fatigue.
- Raison : réduire la friction à l'adoption. La plupart des équipes n'utiliseront pas le write-back initialement.

The bearer-secret pattern to COPY (app/auth/oauth_tokens.py):
```python
import hashlib, secrets
def hash_token(raw: str) -> str:
    return hashlib.sha256(raw.encode()).hexdigest()   # lowercase hex
def mint_access_token() -> str:
    return "oat_" + secrets.token_urlsafe(32)
```
Invite codes mirror this exactly: plaintext = "xbi_" + secrets.token_urlsafe(24)
(≈192 bits — enumeration infeasible); store ONLY sha256(plaintext) hex; a DB leak
yields no usable code. You MAY import hash_token from app.auth.oauth_tokens (DRY).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| plaintext code → DB row | The bearer secret must cross into storage as a sha256 hash only, never as plaintext |
| concurrent redeemers → team_invite_codes.uses | Two racing redemptions must not both pass a max_uses ceiling |
| deleted user / deleted team → invite rows | FK behavior must not orphan or leak codes |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-25-01 | Information disclosure | a DB compromise leaking usable codes | mitigate | mint_code persists ONLY sha256(plaintext) (64-hex) + a non-secret 12-char prefix; the plaintext is returned once and never stored/logged (D-25-01). A leaked row yields no usable code. Unit-proven: plaintext != code_hash. |
| T-25-02 | Spoofing | brute-force / enumeration of codes | mitigate | plaintext = "xbi_" + token_urlsafe(24) (≈192 bits via secrets, CSPRNG) — enumeration infeasible; lookup is by hash (no plaintext timing oracle). |
| T-25-03 | Elevation of privilege | double-spend race exceeding max_uses under concurrency | mitigate | redeem_atomic is a single `UPDATE ... WHERE uses < max_uses RETURNING` — the row lock serializes concurrent redemptions; the loser gets no row (D-25-02). Proven with racing sessions in Plan 03. |
| T-25-04 | Tampering | expiry/revocation checked non-atomically (TOCTOU) | mitigate | revoked_at + expires_at are re-checked INSIDE the same conditional UPDATE that increments uses — no read-then-write window. |
| T-25-05 | Denial of service | deleting a team/user cascading badly or orphaning codes | accept | team_id FK ON DELETE CASCADE (codes die with their team — correct); created_by_user_id ON DELETE SET NULL (code survives creator deletion, audit-safe). Bounded, intentional. |
</threat_model>

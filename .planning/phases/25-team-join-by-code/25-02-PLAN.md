<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → mint/revoke/list endpoints | Only a team admin of THIS team may manage codes |
| client (any authenticated) → join-by-code | The code itself is the authorization; the endpoint must not become an oracle |
| code.team_id → membership write | Redeeming may only add the caller to the code's bound team |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-25-06 | Elevation of privilege | non-admin mints/revokes/lists codes | mitigate | mint/revoke/list all call `_require_team_admin(principal, team, session)` after resolving the team -> 403 for non-admins (D-25-03). Proven in Plan 03. |
| T-25-07 | Information disclosure | list endpoint leaking the hash or a usable code | mitigate | InviteCodeOut has NO code_hash and NO plaintext field — the secret cannot be serialized by construction; only code_prefix + counts + timestamps are returned (D-25-03). |
| T-25-08 | Spoofing | join endpoint acting as an oracle (which codes exist / why one failed) | mitigate | get_by_hash-miss AND redeem_atomic-miss (revoked/expired/exhausted) BOTH return the SAME generic 404 — no distinction leaks (D-25-02). |
| T-25-09 | Denial of service | brute-force redemption attempts | mitigate | enforce_rate_limit(request, JOIN_CODE_RATE_LIMIT, "join-by-code") per-IP before any DB work (D-25-04); high-entropy codes make guessing infeasible regardless. |
| T-25-10 | Tampering | a team-A code adding the caller to team-B | mitigate | add_member is called with `row.team_id` (the code's bound team) — never a client-supplied team; team_scope integrity holds (D-25-04). Proven with a decoy team in Plan 03. |
| T-25-11 | Repudiation | invite mint/join/revoke leaving no trail | mitigate | write_audit on mint / join_by_code / revoke with team_scope + actor + code_prefix (never the secret). |
</threat_model>

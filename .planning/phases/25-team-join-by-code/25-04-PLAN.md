The send-link overlay is the template (popup.html + popup.js):
  - popup.html: a `<div id="sendlink-panel" class="xb-overlay" hidden role="dialog" aria-modal="true">`
    with `.xb-overlay-card` > `.xb-overlay-header` (h3 + a `.xb-icon-btn` close) + `.xb-overlay-body`
    (`.xb-field` groups with <label>/<input>/<select> + a `#sendlink-status` div + `.xb-hint`) +
    `.xb-overlay-footer` (`.xb-btn-secondary` cancel + `.xb-btn-primary` submit). A header trigger
    button lives in `.xb-header-right`: `<button id="btn-send-link" class="xb-icon-btn xb-text-btn">send link</button>`.
  - popup.js: `wireSendLink()` binds open/close/cancel/submit; `openSendLink()` sets panel.hidden=false;
    `setSendLinkStatus(text, type)` toggles the status div (type in {"", "loading","error","success"}).
    All fetches: `const { xbt_token } = await chrome.storage.local.get(["xbt_token"]);` then
    `fetch(`${MEMORY_API_BASE}/v1/...`, { headers: { Authorization: `Bearer ${xbt_token}` }})`.
    `MEMORY_API_BASE = "https://api.grooveos.app"`. `state.activeTeamId` is the current team;
    `state.me` is the /v1/me principal. Wiring functions are called once from the init/boot path
    (find where wireSendLink() is invoked and add wireInvite() beside it).
  - Rendered text uses textContent (never innerHTML) — the contract test's XSS guard scans for it.

Endpoints (Plan 02):
  POST /v1/teams/{activeTeamId}/invite-codes  body {} (defaults) -> 201 {id, code, code_prefix, role, expires_at, max_uses}
      (403 if the caller is not a team admin — surface a clear English message.)
  POST /v1/teams/join-by-code  body {code} -> 200 {team_id, slug, display_name, already_member}; 404 generic; 429 rate-limited.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| popup (client) → memory-api | The extension is untrusted UI; the server enforces admin-gating, rate-limit, and redemption — the client only presents them |
| revealed plaintext code → DOM | The one-time minted code must reach the DOM without becoming an XSS or fabrication vector |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-25-16 | Elevation of privilege | UI implying a non-admin can mint (then confusing 403s) | mitigate | The server 403 is authoritative; mintInvite surfaces a clear "Only a team admin can create invite codes." — the client never fabricates admin state; authZ lives server-side (proven in Plan 03). |
| T-25-17 | Tampering | rendering server strings (code / team name) via innerHTML → XSS | mitigate | The revealed code and join result render via `textContent` only; the contract test's XSS guard scans popup.js for innerHTML carrying such data and fails on a regression. |
| T-25-18 | Spoofing | popup fabricating a code / team membership without the server | mitigate | popup.js hardcodes no code or team; it renders only mint/join responses — the contract test's no-fabricated-data guard enforces this. |
| T-25-19 | Information disclosure | the one-time plaintext lingering in the DOM after close | mitigate | closeInvite clears #invite-code-output.textContent so the reveal does not persist across overlay opens. |
</threat_model>

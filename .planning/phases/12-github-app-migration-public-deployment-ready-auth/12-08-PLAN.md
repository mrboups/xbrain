### Task 1 — Generate the Chrome extension keypair (OPERATOR-ASSISTED, already done per Section 0)

**File(s):** `chrome-extension/.gitignore`, `.planning/KB/chrome-extension-key.md`

**What:** Per Section 0, the operator has already generated the keypair locally. The executor's job here is to (a) gitignore the PEM and (b) write the KB documentation.

**Operator command (reproduced for KB — run once, locally, OUTSIDE the worktree):**

```bash
# Generate 2048-bit RSA private key — KEEP THIS PRIVATE
openssl genrsa -out ~/xbrain-secrets/chrome_ext_private.pem 2048

# Step A — extract base64-encoded DER public key (single line, no whitespace)
#         This is the value for manifest.json "key"
openssl rsa -in ~/xbrain-secrets/chrome_ext_private.pem -pubout -outform DER 2>/dev/null | base64 -w 0
# → Outputs ~392 chars. SAVE for Task 2.

# Step B — compute the resulting chrome.runtime.id (deterministic)
openssl rsa -in ~/xbrain-secrets/chrome_ext_private.pem -pubout -outform DER 2>/dev/null \
  | sha256sum \
  | cut -c1-32 \
  | tr '0-9a-f' 'a-p'
# → Outputs a 32-char a-p string. SAVE for the GitHub App callback URL.
```

The two outputs are needed:
- **(A) base64 pub key** → goes into `manifest.json` Task 2.
- **(B) extension ID** → operator pastes into the GitHub App's "Callback URL" field as `https://<ID>.chromiumapp.org/` (Section 0 operator step 2).

**Executor actions:**

1. Create `chrome-extension/.gitignore` containing:
   ```gitignore
   # Phase 12 — Chrome extension stable-ID keypair.
   # The PRIVATE key is generated locally by the operator, kept outside git,
   # and ONLY needed when publishing to Chrome Web Store (used as the
   # "upload key" to bind the Store listing to the dev key). For unpacked
   # installs, the base64-encoded PUBLIC key in manifest.json is sufficient.
   chrome_ext_private.pem
   chrome_ext_private_*.pem
   *.pem
   ```

2. Create `.planning/KB/chrome-extension-key.md`:
   ```markdown
   # Chrome extension stable-ID key

   Phase 12 (Plan 12-08) makes the unpacked extension's runtime ID
   deterministic by adding a `"key"` field to manifest.json. This is
   required so the GitHub App's registered callback URL
   (`https://<ID>.chromiumapp.org/`) matches every dev/test install
   across machines.

   ## Generation procedure (one-off; do NOT re-run unless the key was lost)

   ```bash
   # Generate the private key OUTSIDE the repo
   openssl genrsa -out ~/xbrain-secrets/chrome_ext_private.pem 2048

   # Step A — base64 pub key → manifest.json "key"
   openssl rsa -in ~/xbrain-secrets/chrome_ext_private.pem -pubout -outform DER 2>/dev/null | base64 -w 0

   # Step B — deterministic extension ID → GitHub App callback URL
   openssl rsa -in ~/xbrain-secrets/chrome_ext_private.pem -pubout -outform DER 2>/dev/null \
     | sha256sum | cut -c1-32 | tr '0-9a-f' 'a-p'
   ```

   ## Where the values live

   | Output | Where |
   |--------|-------|
   | base64 pub key | `chrome-extension/manifest.json` `"key"` field (committed) |
   | extension ID | GitHub App "Callback URL" list (NOT committed; in App settings UI) |
   | private PEM | `~/xbrain-secrets/chrome_ext_private.pem` (NOT committed; gitignored) |

   ## Verification

   After loading the unpacked extension in Chrome:
   ```
   chrome.runtime.id  // must equal the computed ID from Step B
   ```

   If they don't match: the base64 in manifest is wrong (whitespace,
   line-break, or a newer key was generated). Re-run Step A and paste
   exactly the single-line output (no surrounding whitespace).

   ## When to rotate

   - **NEVER** as long as the unpacked extension is in use; rotating
     breaks every installed instance's chromiumapp.org callback.
   - **ONLY** when migrating to Chrome Web Store publication, where the
     Store assigns its own key that overrides this one. At that point
     the manifest `key` field becomes redundant; remove it on the
     Store-published version.

   ## Private key role

   The private PEM is needed exclusively for:
   - Chrome Web Store publication (uploaded as the "upload key" binding
     the listing to this developer identity).
   - Manual signing of CRX bundles for sideloading enterprise distribution
     (not relevant for xbrain v1).

   For day-to-day unpacked development, the private key is not used at all.

   ## References

   - https://developer.chrome.com/docs/extensions/reference/manifest/key
   - https://www.plasmo.com/blog/posts/how-to-create-a-consistent-id-for-your-chrome-extension
   - 12-RESEARCH.md §Q6
   ```

**Why:** Without the documentation, future maintainers (or a Phase 13 publish-to-Web-Store task) won't know where the PEM lives or why the key field exists.

## Section 4 — Risks + Mitigations

- **Risk: operator pastes a base64 string with embedded whitespace / linebreaks.** Mitigation: Task 2 acceptance check `len(m['key']) > 200` catches truncation, but not whitespace embedded in the string. Defensive: use `base64 -w 0` (zero line wrap) in Section 0 — already documented.
- **Risk: existing test users have the OLD random extension ID and break on update.** Mitigation: only 1 user (mrboups) per CONTEXT.md. Communicate: "after the v12 update, the extension ID will change to a stable value — reload the unpacked extension once."
- **Risk: GitHub App callback URLs are NOT registered with the new chromiumapp.org URL.** Mitigation: Section 0 operator step 2 lists the exact URL pattern. Sanity-check pre-execution.
- **Risk: background.js has additional GITHUB_CLIENT_ID references not at line 63.** Mitigation: grep before editing: `grep -n GITHUB_CLIENT_ID chrome-extension/background.js` — confirmed in planning to be a single match.
- **Risk: the deterministic extension ID derivation in Section 0 produces a string the GitHub App rejects.** Mitigation: GitHub accepts ANY URL in the callback list as long as it's syntactically valid. The chromiumapp.org URL is syntactically valid; the only failure mode is "wrong ID" which is caught by the smoke test (sign-in redirect_uri_mismatch error).
- **Risk: `key` field comes BEFORE `manifest_version` and some MV3 tool chokes on the ordering.** Mitigation: Chrome's manifest parser is order-agnostic per official docs; the ordering is purely stylistic. JSON.parse + Chrome load are the only validation gates.
- **REVISION 2 (B-4) — Risk: executor reads "Execute Plan 12-11 first" and halts.** Mitigation: Section 0 reworded to inline the operator checklist; no cross-plan execution dependency exists.

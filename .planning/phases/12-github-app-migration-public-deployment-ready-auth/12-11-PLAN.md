# xbrain GitHub App — architecture (Phase 12)

## Three token types (CRITICAL)

Per RESEARCH §Pattern 1 — these are NOT interchangeable. Confusing them is the #1 source of bugs.

| Token | Prefix | TTL | Use |
|-------|--------|-----|-----|
| App JWT | (none — eyJ...) | 10 min | Mint installation tokens; call `/orgs/{org}/installation`; `/user/{id}`; `/users/{username}/orgs` |
| Installation access token | `ghs_` | 1 hour | Server-to-server: org-membership check, repo writes |
| User-to-server | `ghu_` (refresh: `ghr_`) | 8h / 6mo | Act as user: `/user`, `/user/orgs` (private orgs visible) |

Helpers:
- `mint_app_jwt()` — App JWT only
- `get_installation_token(id)` — ghs_ only
- `get_installation_token_for_org(session, org, force_refresh=False)` — convenience wrapper
- `refresh_user_token_if_needed(session, user)` — ghu_ only

## Installation lookup (hybrid)

`find_installation_for_org(session, org_login)`:
1. DB lookup: `SELECT FROM installations WHERE github_org_login = $1 AND revoked_at IS NULL`.
2. On miss: `GET /orgs/{org}/installation` with App JWT.
   - 200 → backfill the row (UPSERT) and return id.
   - 404 → return None (caller redirects user to install URL).

Self-heals missed webhooks (RESEARCH Pitfall 2).

## Webhook handler

`POST /v1/webhooks/github/installation`:
- HMAC-SHA256 verification (timing-safe via `hmac.compare_digest`) on raw body.
- Dispatches on `X-GitHub-Event` + `payload.action`:
  - `installation.created` → upsert row
  - `installation.deleted` → set `revoked_at`
  - `installation.suspend` → set `suspended_at`
  - `installation.unsuspend` → clear `suspended_at`
  - `installation.new_permissions_accepted` → update `permissions` JSONB
- `installation_repositories` events logged only (no repo perms in v1).
- Raw body MUST be read BEFORE Pydantic parsing (RESEARCH Pitfall 5).

## User token refresh + lookup

`refresh_user_token_if_needed(session, user)`:
- If `expires_at > now + 5min` → return decrypted current token.
- Else acquire per-user asyncio.Lock (RESEARCH Pitfall 6 race fix), re-check inside lock, POST to `/login/oauth/access_token` with `grant_type=refresh_token`.
- ROTATE BOTH tokens atomically AND update `github_access_token_hash` (single-use refresh tokens — GitHub invalidates the old pair on success).
- On error response with body `{"error": ...}` (200 status — GitHub returns 200 even on logical errors), clear stored tokens (and hash) and raise `GitHubReauthRequired`.

`deps.py ghu_ branch` uses `token_lookup_hash(plaintext)` for O(log n) indexed lookup on `users.github_access_token_hash`, then defense-in-depth decrypts to verify the plaintext matches.

## Token storage at rest

- `users.github_access_token_enc` + `github_refresh_token_enc` — Fernet ciphertext (base64 text).
- `users.github_access_token_hash` — HMAC-SHA256 hex (64 chars) — used for indexed lookup in deps.py.
- `FERNET_KEY` shared with Phase 4 drive-sync.
- Rotating `FERNET_KEY` invalidates ALL stored tokens AND hashes — users re-authorize.

## Env vars (Phase 12)

| Var | Purpose |
|-----|---------|
| GITHUB_APP_ID | Optional numeric App ID (client_id is preferred for JWT iss) |
| GITHUB_APP_SLUG | URL slug for install URL: github.com/apps/<slug>/installations/new |
| GITHUB_APP_CLIENT_ID | "Iv23li..." — OAuth client_id for the App |
| GITHUB_APP_CLIENT_SECRET | Paired secret |
| GITHUB_APP_PRIVATE_KEY_B64 | base64-encoded PEM (single line) for JWT signing |
| GITHUB_APP_WEBHOOK_SECRET | HMAC-SHA256 secret for webhook verification |

REMOVED in Phase 12 (Plan 12-04 — verified by verify-phase12.sh assertion 6):
- `GITHUB_API_PAT` / `GITHUB_ORG_PAT` (replaced by installation tokens + App JWT).
- Verified: `grep -r "GITHUB_API_PAT" apps/memory-api/app/ apps/memory-api/tests/ --include="*.py" | grep -v "^#"` returns 0 matches.

PRESERVED but LibreChat-only:

## Frontend client_id

Both `app-site/account/teams/teams.js` and `chrome-extension/background.js` use the SAME `GITHUB_APP_CLIENT_ID` (per RESEARCH §Q11 — GitHub Apps support multi-callback URLs, unlike OAuth Apps).

## Chrome extension stable ID

`manifest.json` `"key"` field forces a deterministic `chrome.runtime.id` across unpacked installs. Procedure in `.planning/KB/chrome-extension-key.md`.

## Failure modes summary

| Failure | User-visible | Recovery |
|---------|--------------|----------|
| Refresh token expired | 401 with "re-authorize" message | User clicks Sign In again |
| App uninstalled mid-session | Membership check returns NOT_MEMBER | Banner shows "install required" |
| Missed installation webhook | Sign-in returns install_required even though installed | First sign-in triggers hybrid-lookup backfill — self-heal within 1 request |
| Installation token revoked mid-use (401 on /members/...) | None | check_github_org_membership force-refreshes once and retries |
| FERNET_KEY rotated | All stored tokens unreadable → user re-authorizes once | Acceptable; documented operator step |
| Network failure mid-refresh | Token rotated client-side may differ from server-side | User re-authorizes once |

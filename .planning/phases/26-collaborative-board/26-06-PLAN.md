<objective>
Wire the two new containers into the stack WITHOUT breaking the OSS-light contract. This is
the plan D-26-04 is about: `verify-phase16.sh` asserts the bare core is EXACTLY ten named
services (an empty `diff`) and that `docker compose config --profiles` equals the literal
string `"integrations ops saas "`. Adding a `board` profile breaks the second assertion
immediately, and both new containers must join the `OPT_IN_CONTAINERS` deny-list that proves
opt-in services do not boot with the core. `verify-phase17-full.sh` carries the same profile
literal plus six `COMPOSE_PROFILES=integrations,saas,ops` invocations, and
`docker-compose.ci-images.yml` must gain both services or CI's override-completeness check
fails and a downstream job would silently rebuild.

Amending those gates is a TASK here, not an afterthought. A green Phase 26 gate and a red
Phase 16 gate on the same commit is a FAILURE.

The board also costs RAM on a VM whose OSS-light budget is documented at ~4 GB for 10
services — which is exactly why both containers are opt-in, `mem_limit`-capped, and outside
the `integrations` profile (that profile drags Neo4j + Langfuse + ClickHouse; a board user
should not have to pay for a graph database).

Purpose: a self-hoster who does nothing gets the same 10-service core they had before. A
self-hoster who wants the board sets one profile.

Output: two compose services, one nginx vhost, the CI image override, both verify scripts
amended, and the operator-facing env/docs updated.

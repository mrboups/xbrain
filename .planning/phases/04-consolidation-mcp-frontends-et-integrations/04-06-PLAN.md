# Plan 04-06 — Multi-folder Drive mapping par équipe

## Goal

Permettre à une équipe d'avoir N dossiers Drive mappés (avec `project_scope` distinct par dossier) au lieu de 1 seul — migration schema + refactor endpoints admin + adaptation du poller.

## Context

**Décision locked (D-06)** :
- Drop `UNIQUE(team_scope)` sur `team_drive_mappings`.
- Add `UNIQUE(team_scope, folder_id)`.
- Add colonne nullable `project_scope VARCHAR(64)`.
- `POST /v1/admin/drive-mapping` accepte `{team_scope, folder_id, project_scope?}` — crée une nouvelle row (ne remplace plus).
- `GET /v1/admin/drive-mapping?team_scope=...` retourne la liste des mappings.
- `DELETE /v1/admin/drive-mapping/{mapping_id}` pour retirer un dossier.
- `drive-sync` : le poller itère déjà sur tous les mappings (`SELECT * FROM team_drive_mappings`) — le multi-folder est gratuit. La seule modification : le `send_to_ingestion_agent` doit passer le `project_scope` du mapping si défini.

**Breaking change dans admin_drive.py** : l'endpoint `GET /admin/drive-mapping/{team_scope}` retourne aujourd'hui un seul objet. Après la migration, il doit retourner une liste. Changer le path en `GET /admin/drive-mapping?team_scope=...` (query param) et ajouter `DELETE /admin/drive-mapping/{mapping_id}`.

**FK drive_watch_channels** : la migration 0005 (plan 04-05) ajoute une FK `drive_watch_channels.mapping_id → team_drive_mappings.id`. La migration 0006 doit être cohérente avec cette FK. Comme 04-06 est Wave 1 et 04-05 est Wave 2 qui dépend de 04-06, la migration 0006 doit être numérotée AVANT la migration 0005 si l'on veut que la FK soit créée après le schema 0006. L'ordre correct dans Alembic :

- 0004 (existant) → 0005 sera renommé 0005_multi_folder (ce plan) → 0006 sera `drive_watch_channels` (plan 04-05 doit donc pointer vers 0005, pas 0004).

**Note** : pour éviter la confusion de numérotation, ce plan crée `0005_multi_folder_drive.py` et le plan 04-05 crée `0006_drive_watch_channels.py` (non `0005`). Les plans sont Wave 1 et Wave 2 respectivement — 04-06 s'exécute en premier.

## Threat Model

- T-04-06-SEC-01 — **DELETE /admin/drive-mapping sans confirmation** : un admin peut supprimer un mapping actif, coupant la sync Drive pour une team. Disposition : **accept** — l'endpoint est admin-only (bridge JWT ou ADMIN_USER_SUBS). La suppression de la watch channel (FK CASCADE) est volontaire — arrêt propre. Le polling backup couvre le gap si le channel est recréé.
- T-04-06-SEC-02 — **OAuth state parameter forgery** (changé de team_scope vers mapping_id) : un attaquant pourrait forger un `state=<mapping_id>` dans le callback OAuth. Mitigation : le code est single-use (expire en 10min, Google le valide côté serveur). Le `mapping_id` ne contient pas d'info exploitable seul. Disposition : **accept** — risque identique à l'implémentation Phase 3, déjà évalué T-03-10-01.

# Phase 5 Plan 03: brain.yaml + GitHub Actions deploy pipeline

## Goal

Définir le schéma `brain.yaml`, créer les templates GitHub Actions pour Cloud Run et Firebase Hosting, écrire le script d'indexing brain, et ajouter l'endpoint `POST /v1/admin/projects` dans memory-api.

## Tasks

### Task 1 — brain.yaml schema + runbook GCP setup

**What:** Documenter le schéma `brain.yaml` (fichier racine de chaque repo GitHub) et le runbook de setup GCP one-shot (activation APIs, IAM, Workload Identity Federation, Firebase init).

**Files:**
- `docs/brain-yaml-schema.md`
- `docs/gitops-setup.md`

**How:**

1. **docs/brain-yaml-schema.md** — documenter le schéma complet de `brain.yaml` avec un exemple annoté (basé sur D1 du CONTEXT.md) :
   ```yaml
   # brain.yaml — fichier de déploiement GitOps xbrain
   # Doit être à la racine du repo GitHub
   name: deck-fundraising          # nom lisible du projet (string, requis)
   type: static                    # static | service | mcp_tool (requis)
   slug: fundraising               # identifiant URL-safe unique dans la team (requis)
   team_scope: acme           # team xbrain propriétaire (requis)
   project_scope: fundraising      # sous-projet dans la team (optionnel, défaut = slug)

   deploy:
     target: firebase              # firebase | cloudrun (requis)
     region: europe-west1          # région GCP (optionnel, défaut europe-west1)

   brain:
     enrich: true                  # indexer le contenu dans xbrain au deploy (bool, défaut false)
     trigger: on_deploy            # on_deploy | daily | on_output (défaut on_deploy)
     content: README.md            # fichier(s) à indexer (string ou list, défaut README.md)
     truth_level: EPHEMERAL        # truth_level initial des items indexés (défaut EPHEMERAL)
   ```

   Documenter les règles de validation :
   - `type: mcp_tool` → le service s'auto-enregistre dans mcp-gateway via brain-index.sh (D6 CONTEXT.md).
   - `slug` doit être lowercase, alphanum + tirets, unique par `team_scope`.
   - Champs requis : `name`, `type`, `slug`, `team_scope`, `deploy.target`.

2. **docs/gitops-setup.md** — runbook one-shot pour configurer GCP (à faire UNE seule fois par projet GCP) :
   - Activer les 4 APIs (run, cloudbuild, artifactregistry, iamcredentials).
   - Créer service account `github-deploy@xbrain-495115.iam.gserviceaccount.com` + 4 IAM roles (RESEARCH.md Q4).
   - Créer Workload Identity Pool + provider OIDC GitHub (commandes gcloud exactes de RESEARCH.md Q4).
   - Firebase init : `firebase init hosting --project xbrain-495115` + créer service account `firebase-deploy@xbrain-495115.iam.gserviceaccount.com` + 4 IAM roles (RESEARCH.md Q5).
   - GitHub Secrets à configurer dans chaque repo : `XBRAIN_BRIDGE_JWT`, `GCP_PROJECT_NUMBER` (Cloud Run), `FIREBASE_SERVICE_ACCOUNT_XBRAIN` (Firebase).

**Test:** Les deux fichiers docs existent et sont valides Markdown. `python3 -c "import yaml; yaml.safe_load(open('docs/brain-yaml-schema.md').read().split('\`\`\`yaml')[1].split('\`\`\`')[0])"` parse sans erreur l'exemple brain.yaml.

### Task 2 — Templates GitHub Actions + script brain-index.sh

**What:** Créer les deux templates de workflow GitHub Actions (Cloud Run et Firebase) et le script shell `brain-index.sh` qui lit `brain.yaml` et POSTe le contenu dans memory-api.

**Files:**
- `.github/workflow-templates/deploy-cloudrun.yml`
- `.github/workflow-templates/deploy-firebase.yml`
- `infrastructure/scripts/brain-index.sh`

**How:**

1. **deploy-cloudrun.yml** — workflow GitHub Actions pour déployer un service sur Cloud Run, basé sur RESEARCH.md Q4. Jobs :
   - `deploy` : checkout → `google-github-actions/auth@v3` (Workload Identity) → setup-gcloud → `gcloud run deploy $SERVICE_NAME --source . --region europe-west1 --project xbrain-495115` → `bash infrastructure/scripts/brain-index.sh` (step brain indexing).
   - Variables d'env et secrets requis documentés en commentaire en-tête du fichier.
   - Permission `id-token: write` pour Workload Identity Federation.

2. **deploy-firebase.yml** — workflow GitHub Actions pour déployer un site statique sur Firebase Hosting, basé sur RESEARCH.md Q5. Jobs :
   - `deploy` : checkout → build step (commande configurable via input) → `FirebaseExtended/action-hosting-deploy@v0` avec `repoToken: ${{ secrets.GITHUB_TOKEN }}`, `firebaseServiceAccount: ${{ secrets.FIREBASE_SERVICE_ACCOUNT_XBRAIN }}`, `projectId: xbrain-495115`, `channelId: live` → brain-index step.

3. **brain-index.sh** — script shell (~40 lignes) qui :
   - Lit `brain.yaml` (requis à la racine du repo, sinon exit 0 — pas d'erreur bloquante).
   - Extrait `slug`, `team_scope`, `project_scope`, `truth_level`, `content` (liste de fichiers à indexer).
   - Pour chaque fichier dans `brain.content`, lire son contenu et POST à `https://api.dejavu.cat/v1/memory/upsert` avec :
     - Header `Authorization: Bearer $XBRAIN_BRIDGE_JWT`
     - Header `X-Team-Scope: <team_scope>`
     - Body JSON : tagging contract complet (content, team_scope, project_scope, truth_level=EPHEMERAL, source=`github:<repo>`, visibility=team, confidence=1.0, validation_status=pending).
   - Si `type: mcp_tool` dans brain.yaml, POST à `https://api.dejavu.cat/v1/tools/register` (pattern register-mcp-tools.sh) pour auto-enregistrer le tool dans mcp-gateway.
   - Log chaque étape. Tout échec d'appel API est loggué mais ne fail pas le script (exit 0 — brain indexing est optionnel).
   - Dépendances : `bash`, `curl`, `python3 -c "import yaml"` (disponible dans ubuntu-latest GitHub Actions). Utiliser `python3 -c "import yaml, sys; d=yaml.safe_load(open('brain.yaml')); print(d.get('team_scope',''))"` pour parser YAML en bash.

**Test:**
```bash
# Test local (sans API réelle)
export XBRAIN_BRIDGE_JWT="fake_jwt"
echo 'name: test\ntype: static\nslug: test\nteam_scope: acme\ndeploy:\n  target: firebase\nbrain:\n  enrich: true\n  content: README.md\n  truth_level: EPHEMERAL' > /tmp/test-brain.yaml
cp /tmp/test-brain.yaml brain.yaml
bash infrastructure/scripts/brain-index.sh
# Attendu : exit 0 même si l'appel API échoue (curl vers api.dejavu.cat non accessible en local)
rm brain.yaml
```

### Task 3 — Endpoint POST /v1/admin/projects dans memory-api

**What:** Ajouter un endpoint admin dans memory-api pour enregistrer les projets déployés (appelé par brain-index.sh après un deploy réussi). Permet au dashboard de lister les projets xbrain avec leur URL et deploy target.

**Files:**
- `apps/memory-api/app/routes/admin_projects.py` (nouveau)
- `apps/memory-api/app/main.py` (enregistrement router)
- `infrastructure/docker-compose.yml` (pas de changement de schema requis — utilise la table `teams` existante ou crée une table légère en mémoire)

**How:**

1. **admin_projects.py** — créer un APIRouter avec deux endpoints :
   ```
   POST /v1/admin/projects
   Body: {
     "slug": "fundraising",
     "name": "Deck Fundraising",
     "url": "https://fundraising.dejavu.cat",
     "team_scope": "acme",
     "project_scope": "fundraising",
     "deploy_target": "firebase",     # firebase | cloudrun
     "type": "static"                  # static | service | mcp_tool
   }
   Auth: Bridge JWT (admin-only — copier guard _is_admin depuis admin_drive.py)
   Returns: 201 avec l'objet projet créé

   GET /v1/admin/projects?team_scope=acme
   Auth: Google ID token OU Bridge JWT
   Returns: liste des projets pour la team
   ```

   Stockage : pour éviter une migration Alembic supplémentaire, stocker dans la table `memory_items` existante avec `source="admin:project"` et le slug comme `id`. Les champs `url`, `deploy_target`, `type` sont dans `metadata` (JSON). Cela permet au dashboard de les retrouver via `GET /v1/admin/projects?team_scope=acme`.

   Alternative (si metadata n'existe pas sur memory_items) : créer une table `projects` avec une migration 0008. Vérifier d'abord avec `\d memory_items` si un champ metadata/extra existe.

2. **main.py** — enregistrer : `app.include_router(admin_projects.router, prefix="/v1/admin", tags=["admin"])`.

**Test:**

## Threat Model

### Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions → api.dejavu.cat | brain-index.sh appelle l'API publique avec un Bridge JWT stocké dans GitHub Secrets |
| GitHub Actions → GCP (Cloud Run/Firebase) | Workload Identity Federation — pas de JSON key file, token OIDC GitHub Actions |

### STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-03-01 | Elevation of Privilege | POST /v1/admin/projects accessible sans auth | mitigate | Guard `_is_admin` appliqué — seul Bridge JWT ou admin Google sub peut créer des projets. |
| T-05-03-02 | Information Disclosure | XBRAIN_BRIDGE_JWT dans GitHub Secrets visible aux collaborateurs avec accès Settings | accept | Risque accepté — les collaborateurs repo sont des membres de l'équipe de confiance. Rotation possible via GitHub Secrets UI. |
| T-05-03-03 | Tampering | brain.yaml modifié par un collaborateur malveillant pour pointer vers team_scope incorrect | mitigate | brain-index.sh ne peut indexer que sous le team_scope déclaré dans brain.yaml. Le Bridge JWT est scopé à une team. Un JWT à scope acme ne peut pas écrire dans un autre team_scope (vérifié par memory-api). |
| T-05-03-04 | Denial of Service | brain-index.sh qui échoue bloque le step de deploy | accept | Script exit 0 sur toute erreur — le deploy lui-même n'est pas bloqué par l'indexing. |

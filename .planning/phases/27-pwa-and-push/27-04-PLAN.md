```python
def user_mention_tokens(*, display_name: str | None, email: str | None,
                        github_username: str | None) -> list[str]:
    """The handles a person can be @mentioned by. Lowercase, [a-z0-9_-] only.

    Derived, never stored: the product has no @handle field, so a mention has to
    resolve against what a member already has. Order is significant for regex
    alternation but _build_mention_regex re-sorts longest-first, so callers get the
    longest-wins behaviour for free.
    """
    # - github_username, as-is when it matches [A-Za-z0-9-]
    # - the email local part, minus any "+tag" suffix
    # - the display name with whitespace removed  ("Ada Lovelace" -> "adalovelace")
    # - the display name's FIRST word                ("Ada Lovelace" -> "ada")
    # de-duplicated case-insensitively, empty/1-char tokens dropped (a 1-char handle
    # would fire on far too much ordinary text)

def detect_user_mentions(content: str, members: list[dict]) -> list[str]:
    """Return the user_ids of team members this message @mentions.

    `members` is [{"user_id", "display_name", "email", "github_username"}]. Uses
    _regex_for() — the SAME cached, boundary-anchored, re.escape'd regex the agent
    detector uses — so `alice@groove.com` and `@adalovelace2` are non-matches here
    for exactly the same reason they are non-matches there.

    Tokens that collide with the reserved agent aliases (effective_aliases(None) plus
    "claude") are excluded: "@agent" summons the agent, never a person.
    """
```
Implementation note: build ONE regex over the union of all members' tokens and map
each captured token back to its user_id (a token -> user_ids dict, since a token may
belong to more than one member). Do not compile one regex per member — a 50-person
team would then compile 50 patterns per message. `_regex_for` is already bounded at
512 entries.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| memory-api -> third-party push service | the encrypted payload and the endpoint URL leave our infrastructure |
| push payload -> recipient's lock screen | the body is visible to anyone holding the device |
| message content -> notification fan-out | an attacker-authored message decides who gets notified |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-27-04-01 | Information Disclosure | push payload contents | mitigate | Payload builders emit only a title, a `PUSH_PREVIEW_CHARS`-capped preview, a first-party app URL and a tag; a test asserts no `xbt_`/`Bearer`/token-shaped field, and the module source is grep-asserted free of those literals |
| T-27-04-02 | Information Disclosure | notification opens a teammate URL | mitigate | The nudge push's `url` is the app origin, never `body.url` — the recipient still passes through the Phase-22 consent gate (D-22-02) instead of the OS opening a stranger's link on a tap |
| T-27-04-03 | Denial of Service | dead endpoint retried forever | mitigate | 404/410 deletes the row (`PRUNE_STATUSES`), so a dead device costs one request once rather than one per message forever |
| T-27-04-04 | Denial of Service | mention fan-out amplification | mitigate | Only members of the sender's own team can be mentioned (member list is team-scoped), self-mentions are skipped, and each send is an independent create_task that cannot block the request |
| T-27-04-05 | Elevation of Privilege | blocked member as target | mitigate | The member list filters `blocked_at is None`, matching the block-enforcement rule already applied to nudge targets (team_chat.py:461-466) |
| T-27-04-06 | Spoofing | forged author label | mitigate | `author_label` is read from the authenticated sender's User row, never from the request body |
| T-27-04-07 | Tampering | log leakage of subscription secrets | mitigate | Only the endpoint HOST is logged; `p256dh`, `auth` and the full endpoint never reach structlog |
</threat_model>

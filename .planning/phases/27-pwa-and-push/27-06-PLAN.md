<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| websocket frame -> DOM | a `team:<id>` publication is authored by another user and rendered into this document |
| websocket frame -> navigation | a `user:<sub>` open_url frame proposes a destination |
| team selector -> API | the client names the team whose history it requests |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-27-06-01 | Tampering | incoming message rendering | mitigate | Rendering is chat-core's `render.js`, which is `innerHTML`-free and grep-asserted so in 27-02; the PWA adds no rendering path of its own (enforced by the fork test) |
| T-27-06-02 | Elevation of Privilege | open_url frame moves the browser | mitigate | No `openDirect` is supplied to `handleOpenUrl`, so the PWA has no auto-open capability at all; the URL is re-validated with `isSafeHttpUrl` at click time and the banner shows the full literal URL (T-22-10) |
| T-27-06-03 | Information Disclosure | requesting another team's history | accept | The team id is client-supplied but `_resolve_team_and_check_membership` (team_chat.py:67-87) rejects non-members and blocked members with 403 before any row is read; the client cannot widen its own access |
| T-27-06-04 | Spoofing | channel subscription | accept | Channel names are built client-side but Centrifugo enforces the server-signed `channels` claim (team_chat.py:136-141) |
| T-27-06-05 | Denial of Service | history paging loop | mitigate | Paging is guarded by `historyPaging` and only fires above the 80 px threshold, and the server caps `limit` at 200 (team_chat.py:163) |
| T-27-06-06 | Information Disclosure | persisted last-team id | accept | Only a team UUID the user is already a member of is stored in localStorage; it is re-validated against `myTeams` on boot and grants nothing on its own |
</threat_model>

```bash
# exit 0 only when FAIL == 0 AND SKIP == 0
```

A standalone node program (no dependencies beyond the vendored Centrifuge file it
imports by path) that proves SC#3.

Sequence:
  1. Read `API_BASE`, `VERIFY_XBT_TOKEN`, `VERIFY_TEAM_ID` and optional
     `VERIFY_XBT_TOKEN_2` from the environment. Any missing required one -> print the
     name and `process.exit(2)`.
  2. RECEIVER: `POST /v1/me/centrifugo-token` with token 2 (or token 1 when absent),
     open a real Centrifugo connection to the returned `ws_url` — assert the URL was
     read from the response, and print it so the log shows a `wss://` the gate did not
     supply.
  3. Subscribe `team:${VERIFY_TEAM_ID}` and wait for the `subscribed` event before
     going further. A publish that races ahead of the subscription would produce a
     false negative.
  4. SENDER: `POST /v1/teams/${VERIFY_TEAM_ID}/messages` with
     `content = "phase27-realtime-probe " + randomUUID()` using token 1 over plain
     HTTP — a genuinely different client from the websocket one.
  5. Wait up to 15 s for a `publication` on the receiver whose
     `data.type === "message"` and whose `data.message.content` CONTAINS the nonce.
     - arrival -> print the elapsed ms and exit 0
     - timeout -> print every frame that DID arrive and exit 1
  6. Always disconnect in a `finally`.

The assertion is ARRIVAL, never absence-of-error: an exit 0 must be impossible unless
a frame carrying this run's nonce was received by a client that never asked for it
over HTTP. Print `RECEIVED nonce=<uuid> after <n>ms` on success so the gate log
carries the evidence.

A python program executed INSIDE the memory-api container
(`docker compose exec -T memory-api python - < infrastructure/scripts/phase27_push_probe.py`)
so it runs against the real pywebpush install, the real VAPID key from the container's
env, and the real Postgres.

It stands up a throwaway HTTP server on `127.0.0.1:<ephemeral>` in a background thread
(`http.server.ThreadingHTTPServer`) whose handler returns a status chosen by the
request path, and records the received headers and body length per path:
  `/ok`   -> 201
  `/gone` -> 410
  `/nf`   -> 404
  `/boom` -> 500

Then, for each of the four, using the REAL code:
  1. create a throwaway user row (or reuse a `VERIFY_USER_ID` passed in the env) and
     `push_subscriptions.upsert(...)` a row whose `endpoint` is
     `http://127.0.0.1:<port>/<path>` with syntactically valid dummy `p256dh`/`auth`
     (a real P-256 public point and a 16-byte auth secret, generated with
     `cryptography` — pywebpush must be able to genuinely encrypt, or the test proves
     nothing about encryption);
  2. `await web_push.send_to_user(session, user_id=..., payload={...})`;
  3. assert the outcome:
     - `/ok`   -> the stand-in RECEIVED a request; row still present; the request
       carried an `Authorization` header starting `vapid ` (or `WebPush `, whichever
       pywebpush 2.3 emits — assert on what it actually sends and record it),
       `Content-Encoding: aes128gcm`, a `TTL` header, and a NON-EMPTY body
     - `/gone` -> row DELETED
     - `/nf`   -> row DELETED
     - `/boom` -> row STILL PRESENT
  4. clean up every row and user it created, in a `finally`.

Print one `PASS:`/`FAIL:` line per assertion and exit non-zero if any failed. Print
the observed request headers for `/ok` (minus the body) so the gate log shows a real
encrypted request rather than a claim.

Note in the module docstring why the endpoint is `http://127.0.0.1` even though
`_is_safe_push_endpoint` requires https: the probe writes through the REPO, not
through the HTTP route, deliberately bypassing the route-level validation whose job
is to stop such an endpoint being stored from outside. The route guard is tested
separately in `tests/test_push_endpoint_safety.py`; this probe is testing the send
and prune behaviour, and needs a socket it can control.

Write the gate in the verify-phase26 house style: `set -uo pipefail`, independent
checks, PASS/FAIL/SKIP counters, a summary line, and **exit 0 only when FAIL == 0 AND
SKIP == 0**. The header comment states plainly that a skipped check is a failure
because a gate that goes green without touching the deployed origin is exactly the
defect class this gate exists to catch.

Checks, in order:

**(a) MANIFEST, DEPLOYED.** `curl -fsS https://grooveos.app/app/manifest.webmanifest`
-> parse with python. Assert `start_url == "/app/"`, `scope == "/app/"`, `display`,
`theme_color`, and at least one 192 and one 512 icon plus one `purpose` containing
`maskable`. Then for EACH `icons[].src`, `curl -sfI "https://grooveos.app${src}"` and
assert HTTP 200 and `content-type: image/png`. Also assert the manifest's own
`content-type` contains `manifest` or `json`.

**(b) SERVICE WORKER, DEPLOYED.** `curl -fsS https://grooveos.app/app/sw.js` -> 200,
`content-type` contains `javascript`, `cache-control` contains `no-cache`. Then, on
the SERVED body with comments stripped
(`sed -e 's://.*::' -e '/\/\*/,/\*\//d'`, then assert on that text — never on the raw
file, since the SW's own comments discuss `/v1/` and `Authorization` and would make a
naive grep self-validating): assert it contains `addEventListener("push"`,
`addEventListener("notificationclick"`, `pushsubscriptionchange`, and all four
non-caching guards (`req.method !== "GET"`, `url.origin !== self.location.origin`,
`/v1/`, `headers.has("Authorization")`). Assert the stripped body contains NO
`cache.put` or `caches.open` inside a branch reachable for a `/v1/` URL — concretely,
assert that the string `/v1/` appears BEFORE the first `respondWith` in the fetch
handler (the guard returns first).

**(c) START URL, DEPLOYED.** `curl -fsS https://grooveos.app/app/` -> 200, and the
body links `manifest.webmanifest`, references `serviceWorker.register`, and contains
neither `requestPermission` nor `pushManager.subscribe` (again on a comment-stripped
copy).

**(d) CORS FROM THE REAL ORIGIN.** A preflight the browser would send:

Assert `access-control-allow-origin: https://grooveos.app` and
`access-control-allow-credentials: true` in the response headers. Then a NEGATIVE
control: the same preflight with `Origin: https://attacker.example` must NOT echo
that origin — a permissive CORS config that passes the positive test is not proof.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| gate environment -> secrets | the gate handles a real xbt_ token and reads the VAPID private key to assert its absence from a response |
| gate -> production data | the gate posts a real message into a real team chat |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-27-08-01 | Information Disclosure | gate log leaking VERIFY_XBT_TOKEN | mitigate | Tokens are passed via environment variables and never echoed; curl uses `-H "Authorization: Bearer $TOKEN"` without `-v`, and the minted centrifugo token is written to a mktemp file that the EXIT trap removes |
| T-27-08-02 | Information Disclosure | gate log leaking VAPID_PRIVATE_KEY | mitigate | Check (h) reads the private key into a shell variable purely to assert its ABSENCE from a response body, never prints it, and unsets it immediately after the comparison |
| T-27-08-03 | Tampering | the gate posting into a real team | accept | The probe messages carry an obvious `phase27-realtime-probe <uuid>` prefix and land in the operator's own team; this is the price of proving arrival against the real system rather than a mock |
| T-27-08-04 | Spoofing | a gate that passes without touching production | mitigate | No `file://` path is permitted, every surface check curls the https origin, and SKIP counts as failure — the three ways a gate normally goes falsely green are each closed |
| T-27-08-05 | Tampering | push probe rows left behind | mitigate | The probe cleans up every row and user it created in a `finally`, and any residue is a subscription pointing at a dead loopback port that the next send prunes on 404 |
| T-27-08-06 | Elevation of Privilege | probe bypassing the route SSRF guard | accept | `phase27_push_probe.py` writes a loopback endpoint through the REPO, not the HTTP route — deliberate and documented; the route guard has its own test (test_push_endpoint_safety.py) and this probe never exercises the route |

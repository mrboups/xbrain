Server (27-03):
```
GET  /v1/push/config      -> {"enabled": bool, "vapid_public_key": "<base64url>"}
POST /v1/push/subscribe   {"endpoint": str, "keys": {"p256dh": str, "auth": str},
                           "user_agent": str|null}   -> 201 {"status": "subscribed"}
                          422 unsafe endpoint · 429 rate limited · 403 non-user principal
POST /v1/push/unsubscribe {"endpoint": str}          -> 204 always
```
All three take `Authorization: Bearer <xbt_token>` — call them through
`api.request(path, {method, body})` from chat_core/api.js, which already attaches it.

Service worker (27-05, app-site/app/sw.js): already has `push` and
`notificationclick` handlers. This plan touches sw.js ONLY to add
`pushsubscriptionchange`.

Client (27-05/27-06): `app-site/app/index.html` has `#btn-enable-push` (rendered
disabled); `app-site/app/app.js` boots the shell; `chat.js` owns the api instance.

Browser API shape:
```js
const reg  = await navigator.serviceWorker.ready;
const perm = await Notification.requestPermission();       // "granted" | "denied" | "default"
const sub  = await reg.pushManager.subscribe({
  userVisibleOnly: true,                                   // required by Chrome
  applicationServerKey: urlBase64ToUint8Array(vapidPublicKey),
});
const json = sub.toJSON();   // { endpoint, keys: { p256dh, auth } }
await sub.unsubscribe();
```
`applicationServerKey` must be a `Uint8Array` — a base64url string is rejected in
Safari. Write the standard `urlBase64ToUint8Array` helper (pad to a multiple of 4,
swap `-`/`_` back to `+`/`/`, `atob`, map to char codes).

Feature detection that actually matters: `"serviceWorker" in navigator`,
`"PushManager" in window`, `"Notification" in window`. iOS Safari exposes all three
ONLY when the app is installed to the Home Screen (`navigator.standalone === true` or
`matchMedia("(display-mode: standalone)").matches`). Detect that case and say so in
the button's hint rather than showing a control that silently cannot work.

Exports:
```js
export function urlBase64ToUint8Array(base64String): Uint8Array
export async function enablePush(api): Promise<{ok: boolean, reason?: string}>
```

`enablePush(api)` order — every rejection returns BEFORE the prompt, so a
mis-configured deployment never burns a user's one-shot permission decision:
  1. feature detection -> `{ok:false, reason:"unsupported"}` (on iOS, additionally
     `reason:"install_required"` when not running standalone);
  2. `Notification.permission === "denied"` -> `{ok:false, reason:"blocked"}` (do NOT
     re-prompt; a denied permission cannot be re-requested);
  3. `const cfg = await api.request("/v1/push/config")`; `cfg.enabled` false or
     `cfg.vapid_public_key` empty -> `{ok:false, reason:"server_disabled"}`;
  4. `await Notification.requestPermission()` — THE prompt; not "granted" ->
     `{ok:false, reason:"denied"}`;
  5. `reg.pushManager.subscribe({userVisibleOnly:true, applicationServerKey:
     urlBase64ToUint8Array(cfg.vapid_public_key)})`;
  6. POST `/v1/push/subscribe` with `sub.toJSON()` plus
     `user_agent: navigator.userAgent.slice(0, 256)`. If the POST fails, call
     `sub.unsubscribe()` and return `{ok:false, reason:"server_error"}` — leaving a
     browser subscription the server does not know about means the device silently
     never receives anything while the UI claims it is on.

`disablePush(api)` — read the existing subscription; POST `/v1/push/unsubscribe`
first (best-effort, swallow errors), THEN `sub.unsubscribe()`. That order is
deliberate: a server row without a live browser subscription is pruned on the first
404/410 send (27-04), while a live browser subscription with no server row is
invisible and unfixable from the app.

`refreshPushButton` sets the button's label and `disabled` state from the real
state — `Notifications off` / `Notifications on` / `Notifications blocked in browser
settings` / `Notifications need the installed app` / `Notifications unavailable` —
and NEVER prompts. English strings only.

`wirePushButton` attaches `btnEl.addEventListener("click", ...)` toggling
enable/disable and re-running `refreshPushButton`. This is the ONLY place
`enablePush` is called.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user gesture -> permission grant | a one-shot, irreversible-from-code decision |
| browser subscription -> server row | the client asserts which endpoint belongs to it |
| service worker rotation -> server state | the browser can change the endpoint without the user |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-27-07-01 | Elevation of Privilege | prompt farming on load | mitigate | One call site inside `enablePush`, reachable only from a click listener; a comment-stripped static gate fails the suite if the prompt appears anywhere else or at top level (D-27-05) |
| T-27-07-02 | Spoofing | claiming another device's endpoint | mitigate | The endpoint comes from `sub.toJSON()`, and the server binds it to the authenticated caller with `ON CONFLICT (endpoint) DO UPDATE SET user_id` (27-03), so a forged claim only ever transfers a mailbox to the browser that actually holds it |
| T-27-07-03 | Information Disclosure | subscription keys in transit | mitigate | `p256dh`/`auth` cross only to `api.grooveos.app` over HTTPS with the bearer token; they are never logged client-side and never written to localStorage |
| T-27-07-04 | Denial of Service | state divergence (browser on, server off) | mitigate | A failed subscribe POST rolls back the browser subscription; disable posts to the server BEFORE unsubscribing locally; `pushsubscriptionchange` re-registers, and any residue is pruned on the first 404/410 (27-04) |
| T-27-07-05 | Repudiation | silent enablement | mitigate | The button's `data-state` and hint always reflect the real `Notification.permission` and subscription, so a person can see and revoke the state they granted (D-27-05 revocable) |
| T-27-07-06 | Information Disclosure | user_agent stored server-side | accept | Capped at 256 chars and used only to label a device in a future device list; it is data the browser already sends on every request |
</threat_model>

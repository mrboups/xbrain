MEMORY-API (the VM):
  The VM is a git checkout tracking origin/main. There is no rsync and no make there.
  NEVER `git clean -fd` on it. Sequence:
    ssh <vm> "cd ~/xbrain && git pull"
    ssh <vm> "cd ~/xbrain/infrastructure && docker compose build memory-api"
    ssh <vm> "cd ~/xbrain/infrastructure && docker compose up -d memory-api"
  Build in SMALL batches — never all images at once (documented OOM trap).
  Alembic runs on boot, so 0029 applies when the container restarts. Confirm it did.

VM .env: every Phase-27 variable must exist there BEFORE the container restarts, or
the container comes up with push silently disabled. The three that matter:
  VAPID_PUBLIC_KEY, VAPID_PRIVATE_KEY, VAPID_SUBJECT
plus, if their defaults are not wanted: PUSH_ENABLED, PUSH_TTL_S, PUSH_PREVIEW_CHARS,
PUSH_SUBSCRIBE_RATE_LIMIT. The generation command is recorded in 27-03-SUMMARY.
The known trap (project memory): VM `.env` has repeatedly lacked variables added in
later phases. Run `bash infrastructure/scripts/preflight-env.sh` before restarting.

ALSO CHECK: `APP_PUBLIC_URL` on the VM must be `https://grooveos.app` — 27-04 builds
every push notification's landing URL from it, and the compiled default is
`http://localhost:8000`, which would send every notification to a dead link.

Gate: `make verify-phase27`, needing `VERIFY_XBT_TOKEN`, `VERIFY_TEAM_ID` and
optionally `VERIFY_XBT_TOKEN_2` exported. Mint a token the way the join page does or
copy one from a signed-in browser's localStorage.

Git Bash note: docker commands carrying an IN-CONTAINER path need MSYS_NO_PATHCONV=1;
commands carrying a HOST path (`-f`, `--env-file`) must NOT have it.

  <name>Task 3: Device verification — no prompt on load, a prompt on click, a visible notification</name>
  <what-built>
    An installable PWA at https://grooveos.app/app/ serving the same team chat as the
    Chrome extension, with opt-in web push on @mentions and on a link nudge.

    Already proven automatically by `make verify-phase27` (recorded in
    27-VERIFICATION.md): the manifest and icons parse and resolve 200 over HTTPS, the
    service worker is served uncached with its four no-caching guards intact, CORS
    admits https://grooveos.app and rejects an attacker origin, a message posted by
    one client ARRIVED at a second websocket client, a real encrypted push reached a
    real socket, and endpoints answering 404/410 were deleted while a 500 was kept.

    What a script cannot prove is what a person sees on a real device: whether the
    browser silently prompted on load, and whether a push turns into a notification
    someone actually notices. That is this checkpoint.
  </what-built>
  <how-to-verify>
    Use a PHONE (Android/Chrome or iOS 16.4+/Safari) plus a second browser on a
    computer signed in as a DIFFERENT team member.

    1. **No prompt on load.** On the phone, open https://grooveos.app/app/ in a normal
       tab. EXPECTED: no notification permission prompt appears at any point while the
       page loads or while you sign in. If one appears, this checkpoint FAILS.

    2. **Sign in.** Tap "Sign in with Google" and use your account. EXPECTED: the team
       chat loads with its history.

    3. **Install.** Android/Chrome: menu -> "Install app" / "Add to Home screen".
       iOS/Safari: Share -> "Add to Home Screen". Open it from the home screen.
       EXPECTED: it opens without browser chrome (standalone), showing the app icon
       you added. On iOS, push works ONLY from this installed copy — if step 5 shows
       "Notifications need the installed app", you are still in the browser tab.

    4. **Prompt on click.** Tap "Notifications off" in the header. EXPECTED: the
       browser's permission prompt appears NOW — and only now. Allow it. The button
       must change to "Notifications on".

    5. **Push on @mention.** From the computer, in the SAME team, send a message that
       @mentions you by your name, e.g. `@<your first name> ping from the gate`.
       EXPECTED: within a few seconds a notification appears on the phone showing the
       sender's name and a short preview. Lock the phone and repeat once —
       it must also arrive with the screen off and the app closed.

    6. **Tap it.** EXPECTED: tapping the notification opens or focuses the installed
       app on /app/. It must NOT open some other website.

    7. **Push on nudge.** From the Chrome extension on the computer, use "send a link"
       to nudge yourself-on-the-phone with any https URL. EXPECTED: a notification
       arrives. Tapping it opens the APP, not the link directly — the link is offered
       in the app with an explicit Open button.

    8. **Realtime, visually.** With the app open on the phone, send a plain message
       from the computer. EXPECTED: it appears in the phone's chat WITHOUT a reload,
       within a second or two.

    9. **Revoke.** Tap "Notifications on" to turn it off, then have the computer
       @mention you again. EXPECTED: no notification arrives. Turn it back on and
       confirm they resume.

    Report back: the phone OS + browser, and for each of the 9 steps whether it
    behaved as expected. If step 1 failed, say so first — a prompt on load is a
    blocking defect, not a cosmetic one.
  </how-to-verify>
  <resume-signal>Type "approved" if all 9 steps behaved as expected, or describe exactly which step deviated and what you saw instead.</resume-signal>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-27-09-01 | Information Disclosure | VAPID private key on the VM | mitigate | The key is written only to the VM `.env` (root-readable, outside the git checkout's tracked files), never committed, never echoed by any deploy command, and its absence from API responses is asserted by gate check (h) |
| T-27-09-02 | Information Disclosure | a secret shipped to a public origin | mitigate | Only the PUBLIC VAPID key ever reaches the client, and it arrives from `GET /v1/push/config` at runtime rather than being baked into a deployed file; the deploy step greps nothing into app-site/ |
| T-27-09-03 | Denial of Service | rebuilding every image at once | mitigate | Only `memory-api` is rebuilt and restarted; the documented batch-of-four OOM trap is respected |
| T-27-09-04 | Tampering | deploying one Firebase target | mitigate | Both targets are deployed in the same command, closing the Phase-10 stale-custom-domain failure |
| T-27-09-05 | Denial of Service | push disabled by a missing env var | mitigate | preflight-env.sh runs before the restart and the gate asserts `enabled: true` plus a 65-byte public key, so a silently push-less deployment cannot pass |
| T-27-09-06 | Spoofing | notification opening a foreign site | mitigate | Device step 6 and step 7 both assert the tap lands on /app/; the nudge push's URL is the app origin by construction (27-04) |

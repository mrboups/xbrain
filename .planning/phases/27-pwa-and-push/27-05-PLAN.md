`fetch` — FOUR guards, each on its own line so each is independently greppable, and
each returning WITHOUT calling `event.respondWith` (which hands the request back to
the network untouched):
```js
self.addEventListener("fetch", (event) => {
  const req = event.request;
  // 1. Only GET is ever cacheable.
  if (req.method !== "GET") return;
  const url = new URL(req.url);
  // 2. NEVER a cross-origin request. api.grooveos.app responses are per-user; this
  //    worker is shared by every profile on the device, so a cached /v1/... response
  //    served to a later, different user on a shared device would be a real leak.
  if (url.origin !== self.location.origin) return;
  // 3. NEVER an API path, even same-origin (defence in depth if the API is ever
  //    reverse-proxied under this origin).
  if (url.pathname.startsWith("/v1/")) return;
  // 4. NEVER a credentialed request.
  if (req.headers.has("Authorization")) return;
  // Cache-first, shell only.
  event.respondWith(caches.match(req).then((hit) => hit || fetch(req)));
});
```
`push` handler: parse `event.data.json()` inside try/catch, fall back to a generic
title; `event.waitUntil(self.registration.showNotification(title, {body, tag,
data: {url}, icon: "/app/icons/icon-192.png"}))`.
`notificationclick`: `notification.close()`, then `clients.matchAll({type:"window",
includeUncontrolled:true})` -> focus an existing `/app/` client if one exists, else
`clients.openWindow(data.url || "/app/")`. The opened URL is ALWAYS a first-party
`/app/` path — never a URL taken from the payload's free-text fields.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| public origin -> localStorage | the PWA holds a bearer `xbt_` token in localStorage on a public web origin |
| service worker -> every profile on the device | one registered worker serves whoever uses that browser next |
| Google Identity Services -> api-token mint | a third-party script supplies the credential that becomes an xbt_ token |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-27-05-01 | Information Disclosure | bearer xbt_ in localStorage | accept | This is the SAME model /join/, /account/login, /account/teams and /account/admin already use on this origin — stated, not silently widened. The token is scoped to one user, revocable server-side, and the alternative (an httpOnly cookie) would need a cross-site cookie between grooveos.app and api.grooveos.app plus CSRF machinery, which is a separate phase. Mitigating controls in scope: `X-Frame-Options: DENY` and `Referrer-Policy: strict-origin-when-cross-origin` already set on both hosting targets; every message field rendered with textContent (27-02) so an XSS path to the token is not opened here |
| T-27-05-02 | Information Disclosure | SW caching an authenticated response | mitigate | Four independent guards in `fetch` (non-GET, cross-origin, `/v1/` path, `Authorization` header) each return before `respondWith`; a shared-device user therefore cannot be served a previous user's API response from cache |
| T-27-05-03 | Tampering | stale service worker | mitigate | `sw.js` is served `no-cache, must-revalidate` on both hosting targets, and `activate` deletes every non-current cache — a bad worker is replaceable within one navigation |
| T-27-05-04 | Elevation of Privilege | SW scope creep | mitigate | Registration and manifest scope are both `/app/`, and `Service-Worker-Allowed: /app/` is set explicitly; the worker cannot intercept `/account/*` or the marketing site |
| T-27-05-05 | Spoofing | notification permission farmed on load | mitigate | No page in this plan references `Notification.requestPermission` or `pushManager.subscribe`; a static test asserts their absence and 27-07 adds exactly one click-gated call site (D-27-05) |
| T-27-05-06 | Tampering | webPlatform.openUrl | mitigate | Re-validates with `isSafeHttpUrl` and opens with `noopener,noreferrer`, mirroring the extension's rule that a URL is re-checked at the point of action |
| T-27-05-07 | Spoofing | Google client id drift | mitigate | A test compares the client id in `auth.js` against the one in `app-site/join/index.html`; a divergence fails the suite rather than producing a silent sign-in outage |

<!-- Endpoint contracts (from Plans 03 + 04). Build the pages against these. -->

POST /v1/auth/local/register   body {email, password}          -> 200 {xbt_token, user:{id,email}, team_scope}
POST /v1/auth/local/login      body {email, password}          -> 200 {xbt_token, user}
                                                                -> 401 {"detail":"Invalid email or password."}
                                                                -> 429 {"detail":"Too many attempts — try again shortly."}
POST /v1/auth/local/set-password  body {new_password, old_password?}  (Authorization: Bearer xbt_) -> 200 {status:"ok"}
                                                                -> 400 {"detail":"Current password is incorrect."}

register also returns team_scope (the solo slug) — the UI stores the xbt_ (localStorage key consistent
with how app-site/account/teams/teams.js reads its token) and can show "signed in as <email>".

UI conventions (mirror app-site/account/teams/index.html): dark theme, JetBrains Mono, inline <style>,
plain fetch(), NO framework, NO bundler. The API base is resolved the same way teams.js resolves it
(read teams.js for the exact origin/base pattern — do NOT hardcode grooveos.app). English strings ONLY
(CLAUDE.md: product/app/code in English; the extension's legacy French is being migrated, do not add new French).

UX note (18-RESEARCH.md Open Question 1): the API deliberately returns a generic 401 for wrong/locked
(no lockout oracle). The UI MAY, after a few client-side failed attempts, show a soft "if this is your
account, wait a few minutes and try again" hint WITHOUT the server confirming account existence — a
client-side heuristic only. Keep the server response generic.
</interfaces>

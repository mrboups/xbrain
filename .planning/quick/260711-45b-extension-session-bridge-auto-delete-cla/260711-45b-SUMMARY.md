# Quick Task 260711-45b: Auto-delete bridged claude.ai conversations Summary

**Added `deleteConversation()` + a best-effort `finally` cleanup in `handleClaude` so every disposable claude.ai conversation created per bridged message is deleted right after the stream ends, keeping the user's real claude.ai chat history clean.**

## Accomplishments

- `handleClaude` now deletes each claude.ai conversation it creates, best-effort, after the `end`/`error` frame is already sent — the response path is completely unchanged and never delayed by cleanup.
- New `deleteConversation(orgId, convUuid)` export (mirrored onto the `globalThis.xbrainClaudeAiClient` MV3 fallback) issues `DELETE .../chat_conversations/{convUuid}` with `credentials: "include"`, throwing on non-2xx so the caller's catch treats it as best-effort.
- New node test (`test_claude_ai_client.mjs`, 3 assertions) proves: (a) DELETE fires exactly once on the just-created conversation, strictly after the `end` frame; (b) a thrown DELETE is swallowed with no `error` frame and chunks/end still delivered; (b2) a non-2xx DELETE response is swallowed the same way.
- `09-CAPTURE.md` now documents the DELETE endpoint contract (table row + BEST-GUESS-PENDING-CAPTURE subsection + A11 PENDING assumption row + a 5-step DevTools capture instruction for the next UAT pass).
- `260711-45b-deferred-items.md` records two explicitly out-of-scope future tracks: native threading (incompatible with delete-per-message) and orgId module-level caching.

## Decisions Made

- Delete-per-message ("piste 1") chosen over native threading because the bridge is provably stateless on claude.ai's side (`openaiToClaudeAi()` always flattens the full history into `prompt` and sends `parent_message_uuid = nil`) — deleting the conversation right after the `end` frame cannot affect any later turn.
- The DELETE endpoint contract is a best guess (standard REST pairing of the create endpoint, expected 204) rather than a live capture, because bridge.grooveos.app has been offline since 2026-06-18 (VM stopped to cut cost) — no end-to-end path is currently available. Documented as A11 PENDING in 09-CAPTURE.md with a concrete DevTools capture procedure for whenever the user next brings the bridge VM up.
- Cleanup failures (network error or non-2xx) are swallowed by an empty `catch` inside the `finally` — this is a deliberate best-effort design per the plan's threat model (T-45b-02): a failed DELETE only means the throwaway conversation isn't cleaned up, never a user-facing failure.

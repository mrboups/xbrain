# Quick Task 260806-5zq — the scraper returns markup, not content

## The evidence that started this

A member posted `https://pitch.digitalaf.xyz/` and asked the agent what the event
was. The agent answered correctly — and it should not have been able to.

Measured against production on 2026-08-06:

| Fact | Value |
|---|---|
| Page fetched by our scraper | yes (`scraper.done bytes=50000`) |
| Characters delivered to the model | 6000 |
| **Readable text inside those 6000** | **306** |
| Position of the real dates in the raw page | offset ~18,300 |
| `"september"` / `"october"` present in the payload | **no** |
| Dates present in the team brain | no |

The answer was right because the Pro/Max path posts to
`claude.ai/api/organizations/.../completion` — claude.ai's own product endpoint,
which fetched the page itself. Our scraped block contributed nothing but 6000
characters of `<script>` and inline CSS.

That fallback exists only on Pro/Max. On the team-API-key path and in the OSS
edition there is none: the same question receives 306 characters of markup.

Second defect, same file: `httpx` sends `user-agent: python-httpx/x.y`, so any
site that filters default clients returns 403. Reproduced on
`en.wikipedia.org` (`scraper.http_error status=403`).

## Prototype result (stdlib, run against the live page)

`html.parser`, dropping `script/style/noscript/svg/head/template/iframe`:

- 58,681 raw bytes → **8,208 characters of text**
- `"september"` lands at offset **1,966** — inside the agent's 6,000-char budget

So the exact fact the agent could not see becomes the fact it reads first.

## Tasks

### Task 1 — extract text, and send a real User-Agent

**Files:** `apps/mcp-scraper/app/main.py`

**Action:**
- Add a stdlib `HTMLParser` subclass that drops non-content elements
  (`script`, `style`, `noscript`, `svg`, `head`, `template`, `iframe`), inserts
  newlines at block boundaries, and collapses runs of whitespace.
- Apply it in `_load_url` **after** the byte cap, so the 50 KB bound still
  guards memory before parsing.
- Send a browser `User-Agent` (plus `Accept` / `Accept-Language`) on the httpx
  request.
- Fail-soft: if parsing raises, fall back to the raw text rather than losing the
  fetch entirely.
- Keep the return type `str` and the tool signature unchanged — `memory-api`
  calls this through the gateway and must not need a matching deploy.

**Verify:** `python -m pytest apps/mcp-scraper/tests/ -q`

**Done:** the tool returns text; markup is gone; the User-Agent is a browser one.

### Task 2 — tests

**Files:** `apps/mcp-scraper/tests/test_extract_text.py`

**Action:** cover the properties, not the wording —
- script/style bodies never appear in the output
- entities are unescaped (`&amp;` → `&`)
- block tags become line breaks rather than glued words
- text far down a long document survives (the regression this fixes)
- malformed HTML does not raise
- the byte cap still applies

**Verify:** all tests pass.

**Done:** the defect has a test that fails against the old implementation.

### Task 3 — deploy and prove it live

**Action:** push, then on the VM rebuild `mcp-scraper` only and restart it.
Re-run the exact measurement from the evidence table through the production
`memory-api` container.

**Done:** readable-text count on `pitch.digitalaf.xyz` is thousands, not 306,
`"september"` is present in the delivered payload, and Wikipedia returns 200.

## Out of scope

- The 6,000-char cap in `team_chat_agent.py` — with extraction it is no longer
  the binding constraint; revisit only if a real page overruns it.
- A "the fetch returned almost no text" signal to the model. Real, worth doing,
  tracked separately — it is a `memory-api` prompt change, not a scraper change.

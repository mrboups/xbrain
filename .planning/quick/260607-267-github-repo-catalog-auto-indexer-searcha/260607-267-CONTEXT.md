# Quick Task 260607-267: GitHub repo-catalog auto-indexer (searchable brain) — Context

**Gathered:** 2026-06-07
**Status:** Ready for planning

<domain>
## Task Boundary

Build a **GitHub repo-catalog auto-indexer** so the model can answer *"which repo handles X / list my org repos"* via `memory_search` instead of guessing repo names.

For each repository a team can access through the xbrain GitHub App installation:
1. Enumerate it (`GET /installation/repositories` via the installation token, resolved per owner from the `installations` table).
2. Generate an **LLM summary of the repo's README** (Claude Haiku).
3. Store the repo as a **searchable brain `memory_item`** carrying the full 7-field tagging contract, with metadata: `full_name`, `description`, `html_url`, `visibility`, `default_branch`, `primary_language`, `topics`, plus the Haiku README summary as (part of) the searchable content.

Keep the catalog fresh on **three triggers**:
1. **Team creation** — index the team's linked GitHub org.
2. **GitHub user sign-in** (`auth_github`) — index/refresh the org(s) the user belongs to where the App is installed.
3. **GitHub `repository` webhook** — `action=created` → add; `renamed` → update; `deleted` → soft-delete the catalog item. (Incremental, not a full re-walk.)

Also expose a **`github_list_repos` read path** (MCP tool on `mcp-github` + a memory-api endpoint) so the catalog can be **listed exactly**, not only semantically searched.

**This is a PLAN-ONLY task.** Produce a reviewable plan; the user approves before any execution. Do NOT execute, deploy, or touch the VM during planning.
</domain>

<decisions>
## Implementation Decisions (LOCKED — do not re-open)

### Description source
- **LLM README summary via Claude Haiku** (`claude-haiku-4-5-20251001`). The token cost is accepted in exchange for better semantic search. Reuse the Phase-13 Haiku plumbing + Anthropic prompt-caching pattern (`RELEVANCE_HAIKU_*` env). Fail-soft: if a repo has no README or Haiku errors/times out, fall back to the GitHub `description` (or a minimal stub) — never block the catalog entry.

### Storage
- **Brain only** — each repo is a `memory_item` written via `memory_provider.upsert(MemoryItem)` (native provider does `INSERT ... ON CONFLICT(id)`). **No new dedicated table.** The `github_list_repos` read path therefore queries the brain (filter by `source='github:repo-catalog'` + `team_scope`), not a bespoke table.

### Scope
- Index **BOTH** the `your-team` org repos (14) **AND** the `mrboups` personal repos (60). i.e. every repo reachable via the installation tokens for both installs.

### Tagging
- `source='github:repo-catalog'`, `truth_level=WORKING`, `project_scope=<repo-name>`, `team_scope=<team>`, plus `visibility`/`confidence`/`validation_status` per the contract. Idempotency: deterministic `id = uuid5(NAMESPACE, f"repo-catalog:{team_scope}:{full_name}")` so re-runs/refresh upsert in place (mirror the team-scope-in-key fix from github_sync).

### Claude's Discretion
- Where exactly to hook trigger (1)/(2) (service vs route), the Haiku prompt + summary length cap, batch size / concurrency for summarizing ~74 READMEs, and the precise `memory_item.content` shape (e.g. `"<full_name> — <summary> [lang, topics, visibility]"`). Decide consistent with the locked decisions + the OSS/self-hostable constraint.
</decisions>

## Specific Ideas / Known reuse points (verified live 2026-06-07)

- **GitHub App `xbrain-auth`** now has `Contents: Read-only` + `Metadata: Read-only`, `repository_selection=all` on both installs: `your-team` org (installation_id 137871175, 14 repos) and `mrboups` user (installation_id 137865560, 60 repos). `GET /installation/repositories` already returns the full lists (verified).
- **Installation tokens:** `app/services/github_installation.py` — `get_installation_token(installation_id)`, `get_installation_token_for_org(session, org)`, `find_installation_for_org`. App JWT: `app/services/github_app_jwt.py::mint_app_jwt`. Installation rows: `installations` table + `app/repos/installations.py` + `app/models/installation.py` (`github_org_login`, `installation_id`, `github_account_type`).
- **Repo contents read:** `app/services/github_contents.py` — `read_repo_file(session, repo, path, ref)` (use it to fetch README.md; 100 KB cap; `GithubPermissionDenied`/`GithubAppNotInstalled`), `list_repo_files`, `_resolve_installation_token` (org → user-install → fallback token).
- **Existing repo→brain sync:** `app/services/github_sync.py` + `POST /v1/internal/github/sync` + mcp-github tool `github_sync_repo` (chunks file contents into `memory_item`s; idempotent uuid5 key includes team_scope; background asyncio task). The catalog is the *lighter* sibling: one summary item per repo, not per-file chunks.
- **mcp-github** is a DIRECT LibreChat MCP server: `apps/mcp-github/app/main.py` (port 8107). Auth `_verify_caller` (xbt_ token path OR LibreChat email path: `X-LibreChat-User-Email` + `X-Internal-Secret == BRIDGE_SHARED_SECRET`); reads are team-neutral. It is a thin proxy → memory-api `/v1/internal/github/*` with a bridge JWT (`app/bridge_jwt.py`). Add the new `github_list_repos` tool here (mirror `github_list_files`).
- **Brain write:** `packages/memory-models` `MemoryProvider.upsert(MemoryItem)`; native provider `INSERT ... ON CONFLICT(id)`. `memory_add` in mcp-github builds a complete MemoryItem (`id` + `created_at`/`updated_at` required — see 260603-29h).
- **Haiku plumbing / prompt cache:** Phase 13 (`RELEVANCE_HAIKU_ENABLED`, `RELEVANCE_HAIKU_MODEL=claude-haiku-4-5-20251001`, timeout, daily token cap). The relevance classifier shows the cache/fail-soft pattern to copy.
- **Webhook:** `app/routes/webhooks_github.py` currently handles `installation` events; the handler must be extended for `repository` events (created/renamed/deleted). Webhook signature/secret validation already exists there.
- **Team ↔ org link:** confirm the github-org field on teams in `app/models/team.py` + `app/repos/teams.py` + `app/services/team_autogrant.py` (auto-grant matches org → team). The catalog's team scoping depends on this mapping.
</specifics>

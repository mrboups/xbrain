## 1. Team ↔ GitHub-Org Link

**Field confirmed:** `Team.github_org` (Column `String(256), nullable=True`) in `apps/memory-api/app/models/team.py` line 24.
[VERIFIED: direct read of team.py]

**Org → team mapping:** `auto_grant_via_org_match` (team_autogrant.py) queries `SELECT teams WHERE github_org IN (user's org_logins)`. The same `teams.github_org` column is the single source of truth. `get_teams_with_github_org(session)` returns all teams with a non-null github_org — used by auth_github signin already.
[VERIFIED: teams.py line 178, team_autogrant.py line 40]

**Problem:** `github_org` holds ONE org per team. The catalog must index repos for the org that owns the team. But the mrboups personal installation is NOT an org — `github_account_type='User'` in the `installations` table. There is no team that maps to `mrboups` via `github_org`. Resolution: the catalog service must enumerate ALL active installations (not only org-type ones), and for each installation call `GET /installation/repositories`. For org-type installations, the `team_scope` is derivable via `Team.github_org == installation.github_org_login`. For user-type installations (mrboups), there is no team FK — the catalog must use a configurable fallback team or write entries to all teams (or be scoped per-install rather than per-team). **Recommendation (Claude's Discretion):** for user-type installations, write catalog items to every team whose members belong to that install; simplest safe choice is to write them to ALL active teams at the time of indexing (same catalog, different `team_scope` copies — one uuid5 per team_scope+full_name as locked). This mirrors what `github_sync_repo` does: the caller supplies `team_scope` explicitly. The background indexer for trigger (1)/(2) knows the team from the signing-in user's membership.

**Team-creation hook (trigger 1):** `create_team` in `repos/teams.py` is the single place a team is created. It does NOT fire any background work today. The catalog hook should be added in the route that calls `create_team` — specifically `app/routes/teams.py` POST /v1/teams or POST /v1/teams/self-solo — as a `asyncio.create_task(index_team_catalog(team.slug, team.github_org))` after commit, guarded by `if team.github_org` for org teams.
[VERIFIED: repos/teams.py line 13-35]

**Sign-in hook (trigger 2):** `signin_github` in `app/routes/auth_github.py` already resolves `profile["org_logins"]` and calls `auto_grant_via_org_match`. The catalog hook goes at Step 9 (after commit, alongside `emit_autogrant_notifications`) as another `background_tasks.add_task(index_orgs_catalog, org_logins=profile["org_logins"], session_factory=...)`. The function only indexes orgs that have an active installation — skip orgs with no installation row.
[VERIFIED: auth_github.py lines 422-485]

## 2. GitHub API Specifics

### GET /installation/repositories — Enumerate all repos for an install

**Endpoint:** `GET https://api.github.com/installation/repositories`
**Auth:** `Authorization: Bearer <ghs_ installation token>`
**Pagination:** `per_page` (max 100) + `page` (1-indexed). Mirrors the pattern already used in `_fetch_github_profile` (`/user/orgs`) at auth_github.py lines 167-178.
**Headers already defined in codebase:** `{"Accept": "application/vnd.github+json", "X-GitHub-Api-Version": "2022-11-28"}` — reuse `_GH_HEADERS` constant from `github_contents.py` line 38.
[VERIFIED: _GH_HEADERS in github_contents.py]

**Fields returned per repo object (no preview headers needed under `X-GitHub-Api-Version: 2022-11-28`):**
- `full_name` (e.g. `your-team/xbrain`)
- `description` (nullable string)
- `default_branch` (e.g. `main`)
- `language` (primary language, nullable)
- `visibility` (`public` or `private`)
- `private` (boolean — redundant with visibility but both present)
- `topics` (array of strings — included in the standard response since 2020; NO preview Accept header required under the `2022-11-28` API version)
- `html_url`, `name`, `owner.login`
[ASSUMED: topics field availability — GitHub docs state topics are part of the standard repo object under the stable API version. Verify at implementation time if topics returns empty vs absent for repos with no topics.]

**Rate limit:** Installation tokens get 5,000 requests/hour per installation. 74 repos = 1 API call to list (fits in one page of 100) + up to 74 README fetches = 75 total calls. No rate-limit concern. For ongoing webhook-driven upserts the cost is 1-2 calls per event.
[ASSUMED: rate limit numbers from GitHub App documentation. Acceptable confidence given the small repo count.]

### README fetch

**Recommended endpoint:** `GET /repos/{owner}/{repo}/readme` — returns the repository's default README at whatever path it exists (README.md, readme.rst, README, etc.). Response body: `{"content": "<base64>", "encoding": "base64", "size": <bytes>, ...}`.

**Reuse path:** `read_repo_file(session, repo, "README.md", ref="HEAD")` in `github_contents.py` — already does base64 decode, 100 KB cap, returns `{"content": str, "truncated": bool, "size": int}`. However `read_repo_file` raises `ValueError("Path 'README.md' not found...")` on 404. The catalog service must catch ValueError and fall back to `repo["description"]`. Alternatively, call the dedicated `/readme` endpoint directly (doesn't require knowing the filename) and handle 404 by falling back — slightly more robust. **Recommendation:** use `read_repo_file(session, repo, "README.md")` for reuse; catch `ValueError` + `GithubPermissionDenied` for fail-soft. If README.md 404s, try `README.rst` then fall back to description.
[VERIFIED: github_contents.py lines 215-303]

3. Budget check via `_check_budget` / `_record_tokens` (in-memory daily per-team counter) — already handles `RELEVANCE_DAILY_TOKEN_CAP_PER_TEAM`.

## 4. Webhook `repository` Event — Integration Point

**Existing handler:** `app/routes/webhooks_github.py`
- Single endpoint: `POST /v1/webhooks/github/installation` (line 144)
- Signature verification: `_verify_signature(raw_body, X-Hub-Signature-256)` — timing-safe HMAC-SHA256, fail closed (503 if secret not set, 401 on mismatch). Raw bytes read BEFORE JSON parse — pattern MUST be preserved.
- Dispatch: `if event == "installation"` / `elif event == "installation_repositories"` / `elif event == "ping"` / `else` log-and-200.

**Adding `repository` event support:**
1. Add a new branch `elif event == "repository" and isinstance(payload, dict): await _handle_repository_event(session, payload)`.
2. `_handle_repository_event` reads `payload["action"]` and `payload["repository"]`:
   - `created` → fire-and-forget `asyncio.create_task(upsert_catalog_item(session_factory, payload["repository"], action="created"))`
   - `renamed` (old name in `payload["changes"]["repository"]["name"]["from"]`) → upsert the new item + soft-delete the old one (key changes since full_name changes)
   - `deleted` / `privatized` → soft-delete the catalog item
   - `publicized` → re-upsert (visibility changed; update the item)
   - `edited` (description changed) → re-upsert
3. The route already returns 200 for all signature-verified payloads — no change to response shape.

**OPERATOR STEP REQUIRED:** The GitHub App `xbrain-auth` is currently subscribed to `installation` and `installation_repositories` events only. Adding `repository` event support requires:
> GitHub App settings (https://github.com/settings/apps/xbrain-auth) → Permissions & events → Subscribe to events → check **Repository** → Save.
This is a zero-downtime operator step. The webhook code must be deployed first (so the handler exists when events start arriving), or the app subscribes after the code is deployed.

## 5. `github_list_repos` — Exact Listing Read Path

**Current state:** No source-filtered list endpoint exists. `GET /v1/memory/search` is semantic (vector search). `GET /v1/memory/{item_id}` is by ID. There is no `GET /v1/memory?source=X&team_scope=Y` query endpoint today.
[VERIFIED: memory.py lines 383-410, native_provider.py lines 187-299]

**Recommended approach — new internal endpoint (lightest option, brain-only, no new table):**
Add `GET /v1/internal/github/catalog` to `app/routes/internal_github.py`:
```python
@router.get("/internal/github/catalog")
async def github_catalog(
    team_scope: str = Depends(get_team_scope),
    session: AsyncSession = Depends(get_session),
    principal = Depends(get_current_principal),
) -> dict:
    pool = await provider._ensure_pool()
    async with pool.acquire() as conn:
        rows = await conn.fetch(
            "SELECT id, content, metadata, created_at, updated_at "
            "FROM memory_items "
            "WHERE source = 'github:repo-catalog' "
            "  AND team_scope = $1 "
            "  AND deleted_at IS NULL "
            "ORDER BY updated_at DESC",
            team_scope,
        )
    return {"repos": [dict(r) for r in rows]}
```
This is a direct asyncpg SELECT — no Qdrant, no embedding, no new table. The `memory_items.source` column is indexed (confirmed from migration 0003/0004 pattern) and the query is bounded by team_scope.

**Alternative:** add a `list_by_source(source, team_scope)` helper to `NativeProvider` and call it from a new endpoint. Slightly cleaner but more code. For a single use-case, the inline raw query in the route is acceptable (pattern already exists in multiple routes).

**MCP tool `github_list_repos`:** Add to `apps/mcp-github/app/main.py` following the `github_list_files` pattern:
- `_resolve_team(ctx)` for auth (returns bearer + team_scope)
- `GET /v1/internal/github/catalog` with `X-Team-Scope: <team_scope>` header
- Return JSON array of repo metadata (full_name, summary, language, topics, visibility, html_url)

## 6. Pitfalls and Constraints

### Pitfall 1: Backfill blocks the sign-in / team-create request
74 Haiku calls at ~900ms each = ~66 seconds sequential. Must be fire-and-forget.
**Prevention:** `asyncio.create_task(...)` after commit, using `async_session_factory()` for a fresh DB connection. Cap concurrency via `asyncio.Semaphore(5)` inside the background indexer (5 concurrent README fetches + Haiku calls = ~13 seconds total). Mirror the `_run_sync` background task in `internal_github.py`.

### Pitfall 2: Idempotency — duplicate items when a repo is reachable by both installs
Both `your-team` (org install) and `mrboups` (user install) can see some of the same repos if mrboups is a member of your-team. The uuid5 key `uuid5(NS, f"repo-catalog:{team_scope}:{full_name}")` includes `team_scope` — so if the same repo is written under `team_scope=your-team` by the org install AND by the user install, they get the same uuid5 key and the second write is a no-op upsert. This is correct behavior.
If the same repo is written for two DIFFERENT teams, they get different keys (different team_scope) — each team sees its own copy. Also correct.

### Pitfall 3: Soft-delete support confirmed
`NativeProvider.mark_deleted(item_id, deleted_at)` exists (line 332 of native_provider.py): sets `deleted_at_ts` in Qdrant payload + PG `deleted_at` column. `brain-janitor` hard-purges rows after 30 days. The `repository.deleted` webhook handler must call `provider.mark_deleted(item_id, datetime.now(utc))` — the item_id is retrieved via a raw PG SELECT on `source='github:repo-catalog' AND team_scope=$1 AND metadata->>'full_name'=$2`.
[VERIFIED: native_provider.py lines 332-360]

### Pitfall 4: `renamed` webhook — key invalidation
On `repository.renamed`, `payload["repository"]["full_name"]` = new name; `payload["changes"]["repository"]["name"]["from"]` = old base name (not full_name). Old `full_name = owner + '/' + old_name`. Must soft-delete the old uuid5 key and upsert a new one. Two operations, must both succeed — run them in sequence inside the background task (soft-delete then upsert, not the reverse).

### Pitfall 5: Team scope for mrboups personal repos
Personal install (`github_account_type='User'`) has no `teams.github_org` match since no team has `github_org='mrboups'`. Strategy: at backfill time (trigger 2 — sign-in), the signer's team(s) are known — write catalog items scoped to each team the user belongs to. At team-create time (trigger 1), only org-type installs are relevant (skip user installs). For the webhook path (trigger 3), `payload["installation"]["account"]["type"]` distinguishes User vs Organization — for User installs, look up the owning user's team memberships at webhook time.

### Pitfall 6: `memory_items.source` CHECK constraint
Migration 0023 widened `source` to `VARCHAR(32)` with a CHECK constraint. Confirm `'github:repo-catalog'` fits (17 chars) and is not blocked by the CHECK. Read migration 0023 to verify.
[ASSUMED: the CHECK constraint text was not read — verify during implementation that `github:repo-catalog` passes the constraint, or that the column is unconstrained by CHECK.]

### Pitfall 7: README fetch fallback order
`read_repo_file(..., "README.md")` raises `ValueError` on 404. For repos with `readme.md` (lowercase) or `README.rst`, the uppercase `README.md` fetch will 404. The dedicated `GET /repos/{o}/{r}/readme` endpoint is case-insensitive and finds any README variant. **Prefer the `/readme` endpoint** over `read_repo_file("README.md")` to maximize README coverage. Call it directly with the installation token rather than reusing `read_repo_file`.

## 7. memory_item Content Shape (Claude's Discretion)

Recommended `content` string (optimized for semantic recall):
```
{full_name} — {haiku_summary_or_description}
Language: {primary_language}. Topics: {topics_joined_or_none}. Visibility: {visibility}.
```

Recommended `metadata` dict:
```json
{
  "full_name": "your-team/xbrain",
  "html_url": "https://github.com/your-team/xbrain",
  "default_branch": "main",
  "primary_language": "Python",
  "topics": ["ai", "memory"],
  "visibility": "private",
  "readme_summarized": true,
  "installation_id": 137871175
}
```

The `content` field is what Qdrant embeds for semantic search — making it human-readable and keyword-rich ensures `memory_search("which repo handles auth")` returns the right repo.
